# ЧАСТЬ 0. Зачем нужно профилирование (база для любого вопроса)

**Профилирование** — измерение того, *где программа тратит время и ресурсы*, чтобы оптимизировать **узкое место (bottleneck)**, а не «всё подряд».

Принципы:
1. **Сначала измерь — потом оптимизируй.** Интуиция о «горячих местах» часто неверна.
2. **Закон Амдала:** ускорение всей программы ограничено долей, которую не ускорили. Оптимизировать ядро, занимающее 2% времени, бессмысленно.
3. **Цикл оптимизации (APOD):** Assess (оценить, найти горячие точки) → Parallelize → Optimize → Deploy, и снова по кругу.
4. **Два уровня анализа** (ключевая идея презентации):
   - **Уровень приложения** (где система простаивает: CPU/GPU, копирования, синхронизации, перекрытие) → **Nsight Systems**.
   - **Уровень ядра** (почему конкретное CUDA-ядро медленное: память, вычисления, задержки) → **Nsight Compute**.
5. **Два способа сбора данных:**
   | Метод | Суть | Плюсы / минусы |
   |-------|------|----------------|
   | **Tracing (трассировка)** | Записываются **все** события (вызовы API, запуски ядер, копирования) с временными метками | Точно, полная картина; объём данных большой, небольшие накладные расходы |
   | **Sampling (семплирование)** | Периодически (напр., ~1 кГц) прерывает процесс и записывает, где выполняется код (IP/стек) | Малые накладные расходы, статистическая картина «где горячо»; пропускает короткие события |
   | **Сбор аппаратных счётчиков (counters/metrics)** | Читаются счётчики GPU во время работы ядра | Очень детально, но дорого (ядро запускается **несколько раз** — replay) |
6. **Эффект наблюдателя:** любой профайлер вносит накладные расходы (overhead); чем детальнее данные — тем он выше. Поэтому nsys (лёгкий) используют первым, ncu (тяжёлый) — точечно.

# ЧАСТЬ 1. Слайд 6 — «CUDA® Profiling Tools» (устаревшие инструменты, перечёркнуты)

## Что на слайде

- **nvvp** — NVIDIA Visual Profiler (графический профайлер).
- **nvprof** — консольный профайлер для CUDA-, OpenACC- и OpenMP-приложений.
- Возможности «уровня приложения» (Application level):
  - общая производительность приложения: **перекрывать (overlap) работу CPU и GPU**, находить узкие места (CPU или GPU);
  - общая загрузка и эффективность GPU: **перекрывать вычисления и копирования памяти**, эффективно использовать **compute engines** и **copy engines**.
- Возможности «уровня ядра» (Kernel level):
  - эффективное использование **пропускной способности памяти**;
  - эффективное использование **вычислительных ресурсов**;
  - **скрытие задержек** инструкций и памяти (latency hiding).
- Пример анализа зависимостей: `nvprof --dependency-analysis --cpu-thread-tracing on ./executable_cuda`.
- **Всё перечёркнуто красным**, стрелка → **Nsight Systems** и **Nsight Compute**.

## Что это значит

- **nvvp и nvprof устарели (deprecated)** и заменены семейством Nsight. Они не поддерживают новые архитектуры GPU (начиная примерно с Turing/Ampere и новее — для них профилирование возможно только через Nsight Systems/Compute), и убраны из новых версий CUDA Toolkit.
- Распределение функций nvprof:
  - **таймлайн, копирования, API-вызовы, синхронизация** → **`nsys`** (Nsight Systems);
  - **метрики/счётчики ядер** (`--metrics`, `--events`) → **`ncu`** (Nsight Compute).
- Разделение уровней на слайде — это и есть разделение между двумя новыми инструментами.

## Понятия со слайда

- **Overlap CPU и GPU:** запуск ядер асинхронный — пока GPU считает, CPU должен готовить следующую порцию, а не простаивать.
- **Overlap compute и memory copies:** копирование `cudaMemcpyAsync` в одном stream параллельно с ядром в другом stream; требует **pinned (page-locked) памяти** хоста.
- **Compute engine / copy engines:** у GPU есть отдельные аппаратные блоки: движок вычислений (SM) и один или несколько **DMA-движков копирования** (HtoD, DtoH). Их можно загружать одновременно.
- **Latency hiding:** задержка доступа к глобальной памяти (сотни тактов) скрывается переключением между многими готовыми warp — поэтому нужна высокая **occupancy** (заполняемость).
- **Dependency analysis** (у nvprof) — анализ **критического пути** между CPU и GPU: какие операции на самом деле ограничивают общее время.

> ⚠ Ловушка: «nvprof ... OpenMP» — слайд пишет, что nvprof поддерживает OpenACC/OpenMP; корректнее: он показывал активность GPU, порождённую такими программами (через CUDA), но полноценную трассировку OpenMP/MPI/OpenACC даёт именно Nsight Systems.
> ⚠ Ловушка: nvprof — замена не «один к одному»: старый один инструмент разделился на два.

**Смысл:** профилирование — это **цикл**:
1. Начинаем с **Nsight Systems** — смотрим всю программу целиком, находим, **что** и **где** тормозит (CPU? копирования? синхронизации? простои GPU?).
2. Находим самые «тяжёлые» CUDA-ядра → **«ныряем»** в них через **Nsight Compute** (сбор метрик/счётчиков) и оптимизируем реализацию ядра, использование GPU, доступ к памяти.
3. Для графических задач — «ныряем» в кадры через **Nsight Graphics**.
4. После правок снова **проверяем общее поведение** (Recheck overall workload behavior) в Nsight Systems.
5. Если производительность удовлетворительна — **заканчиваем** (Finished).

## Три основных инструмента

| Инструмент | Назначение (по слайду) | Что оптимизируем |
|------------|------------------------|------------------|
| **Nsight Systems** (`nsys`) | Анализ приложения/алгоритма **в масштабе всей системы** (system-wide) | синхронизация, перемещение данных, перекрытие/параллелизм |
| **Nsight Compute** (`ncu`) | Отладка и оптимизация **конкретных CUDA-ядер** | использование GPU, реализация ядра, доступ к памяти |
| **Nsight Graphics** | Отладка и оптимизация **графических нагрузок** | рендеринг кадров, шейдеры, синхронизация |

- На слайде: **«nvprof replaced with nsys –profile....»**, ссылка https://developer.nvidia.com/nsight-systems.
- ➕ Есть и другие члены семейства: Nsight Visual Studio Edition / Eclipse Edition (IDE-интеграции с отладкой), Nsight Deep Learning Designer, Nsight Aftermath SDK (разбор аварий GPU в играх) и др. Для **отладки** ядер (поиск ошибок, а не производительности) используются **cuda-gdb** и **compute-sanitizer** (бывший cuda-memcheck).

> ⚠ Ловушка (опечатки слайда): «optomize» = optimize; «conters» = counters; «Debug/&optomize» — читать «Debug & optimize».
> ⚠ Ловушка: фраза «nvprof replaced with nsys» упрощена — часть возможностей nvprof (метрики ядер) перешла в **ncu**.
> ➕ Поэтому на вопрос «чем профилировать, если программа работает медленно, а причина неизвестна?» ответ — **сначала nsys** (широкий взгляд), **потом ncu** (узкий и глубокий).

# ЧАСТЬ 3. Слайд 10 — «NVIDIA Nsight Systems»

## Что на слайде и что это значит

1. **Даёт более полную картину того, как код распределяет нагрузку между несколькими CPU и GPU.**
2. **Помогает найти возможности оптимизации и выявить проблемы:**
   - **GPU starvation** («голодание» GPU) — GPU простаивает, потому что ему **не подают работу** вовремя;
   - **недостаточное распараллеливание или конвейеризация (pipelining) на CPU**;
   - **неожиданно «дорогой» алгоритм** на CPU или GPU;
   - **лишняя синхронизация GPU**.
3. **Низкие накладные расходы:** используются **tracing + sampling**, собираются данные об активности процессов и потоков; визуализируются **миллионы событий** на быстрой GUI-временной шкале (timeline).
4. **Корреляция данных между ядрами CPU и потоками (streams) GPU** — позволяет исследовать узкие места (видно, какой вызов CPU породил какое ядро GPU).
5. **Мультиплатформенность:** Linux и Windows; x86-64, Tegra (Arm, встраиваемые Jetson/Drive), Power; **MacOSX — только как host** (т.е. GUI можно запускать на Mac для просмотра отчётов, а профилируемое приложение — нет).

## Разбор терминов

- **GPU starvation:** GPU «голодает» — на его временной шкале **пробелы** между ядрами. Причины: медленная подготовка данных на CPU (загрузка с диска, препроцессинг), накладные расходы запуска ядер, лишние синхронизации, ожидание копирований.
- **Pipelining (конвейеризация):** CPU готовит порцию *N+1*, пока GPU обрабатывает порцию *N*.
- **Timeline (временная шкала):** по оси X — время; по оси Y — строки: потоки CPU (с цветом состояния: выполняется/ожидает/заблокирован), вызовы API (CUDA API, cuDNN, cuBLAS, OS runtime, NVTX, MPI), и GPU: **streams**, ядра (**Kernels**), память (**Memory**: HtoD, DtoH, DtoD, Memset).
- **Stream (поток CUDA):** очередь команд на GPU; команды внутри одного stream выполняются по порядку, в разных — могут параллельно.

## ➕ Что именно собирает nsys

- **Трассировка API:** CUDA Runtime/Driver API, cuBLAS, cuDNN, NVTX, OS runtime (pthread, файловый ввод-вывод, `pthread_cond_wait` и т.п.), MPI, OpenACC, OpenMP (OMPT), OpenGL/Vulkan/DirectX, NCCL.
- **Семплирование CPU** (IP/backtrace sampling): периодически снимается стек — получаем «bottom-up» и «top-down» таблицы горячих функций CPU.
- **Context switches** потоков ОС (опционально).
- **Использование памяти GPU, GPU-метрики** (низкочастотная выборка загрузки SM, пропускной способности и т.п.) — но **не** детальные метрики ядер (это работа ncu).
- Формат отчёта: **`.nsys-rep`** (в старых версиях — **`.qdrep`**); экспорт в **SQLite** и другие форматы.

> ⚠ Ловушка: nsys **не** объясняет *почему* ядро медленное внутри (какая инструкция, какой кэш-промах) — он показывает *когда* и *как долго*. Для «почему» — Nsight Compute.

# ЧАСТЬ 4. Слайд 11 — «Command Line Options nsys» (команды CLI)

Утилита называется **`nsys`**, формат: `nsys <команда> [опции] [приложение и его аргументы]`.

| Команда | Что делает (по слайду) | Пояснение |
|---------|------------------------|-----------|
| **`profile`** | «Полностью определённое профилирование»: не требует дополнительного ввода. Опции определяют, когда начинается/заканчивается сбор, какие **коллекторы** используются (API trace, IP sampling и т.д.), какие процессы мониторятся | Основная команда: **запустить приложение и собрать отчёт за один шаг** |
| **`start`** | Начать сбор в **интерактивном режиме**. Можно выполнить **до или после** `launch` | Интерактивный режим: профилируем часть работы |
| **`stop`** | Остановить сбор, начатый в интерактивном режиме. Все активные сборы останавливаются, **CLI-процесс завершается, но приложение продолжает работать** | Приложение не убивается |
| **`cancel`** | Отменяет существующий сбор интерактивного режима; **все уже собранные данные отбрасываются** | В отличие от `stop` — отчёта не будет |
| **`launch`** | В интерактивном режиме **запускает приложение** в окружении, поддерживающем запрошенные опции. Можно до или после `start` | Приложение запущено, но сбор ещё не идёт |
| **`shutdown`** | Отключает CLI-процесс от запущенного приложения и **принудительно завершает CLI-процесс**. Если сбор ожидает или активен — он **отменяется** | |
| **`export`** | Создаёт файл экспорта из существующего `.nsys-rep` (форматы экспорта — в каталоге `/documentation/nsys-exporter` установки) | Например, в SQLite/JSON/текст для анализа скриптами |
| **`stats`** | Постобработка существующего результата (**`.nsys-rep` или SQLite**) для **статистической информации** | Таблицы: суммы по API, ядрам, копированиям |
| **`analyze`** | Постобработка результата для создания отчёта **экспертной системы** (expert systems report) | Автоматические подсказки о типичных проблемах |
| **`status`** | Сообщает о состоянии CLI-сбора или **пригодности окружения** для профилирования | Проверка (`nsys status -e`), напр. права доступа |
| **`sessions`** | Информация о **всех сессиях**, запущенных в системе | Связано с «multiple simultaneous sessions» |

Документация: https://docs.nvidia.com/nsight-systems/UserGuide/index.html

## ➕ Практика: типичные вызовы

```bash
# Базовый запуск: трассировка CUDA и NVTX, вывод статистики в консоль
nsys profile -t cuda,nvtx --stats=true -o report ./app

# Только отчёт (.nsys-rep создаётся автоматически с суффиксом)
nsys profile -o report ./app            # → report.nsys-rep

# Перезапись существующего отчёта
nsys profile -f true -o report ./app

# Посмотреть статистику уже собранного отчёта
nsys stats report.nsys-rep

# Открыть GUI (можно на другой машине, например на ноутбуке)
nsys-ui report.nsys-rep

# Экспорт в SQLite
nsys export --type sqlite report.nsys-rep

# Автоматический «экспертный» анализ
nsys analyze report.nsys-rep
```

Часто используемые опции `nsys profile` (смысл важно знать):

| Опция | Смысл |
|-------|-------|
| `-t` / `--trace` | какие API трассировать: `cuda`, `nvtx`, `osrt` (OS runtime), `cublas`, `cudnn`, `mpi`, `openacc`, `openmp`, `opengl`, `vulkan`, `none`… (можно перечислять через запятую). По умолчанию включены cuda, nvtx, osrt, opengl |
| `-o` | имя выходного файла (без расширения) |
| `-f true` | перезаписывать существующий отчёт |
| `--stats=true` | после завершения вывести сводную статистику (аналог вызова `nsys stats`) |
| `-s` / `--sample` | семплирование CPU (`cpu`/`none`) |
| `--cuda-memory-usage=true` | отслеживать использование памяти CUDA |
| `--delay N`, `--duration N` | начать сбор через N секунд / собирать N секунд |
| `--capture-range=cudaProfilerApi` | собирать только между вызовами `cudaProfilerStart()` и `cudaProfilerStop()` в коде |
| `--capture-range=nvtx` | собирать внутри заданного NVTX-диапазона |
| `--force-overwrite`, `--export=sqlite` | перезапись, автоэкспорт |

Стандартные сводные таблицы статистики (`nsys stats`): **API-вызовы CUDA** (cuda_api_sum), **время ядер GPU** (cuda_gpu_kern_sum), **время и размер копирований** (cuda_gpu_mem_time_sum, cuda_gpu_mem_size_sum), **NVTX-диапазоны** (nvtx_sum), **вызовы OS runtime** (osrt_sum). Столбцы: Time(%), Total Time, Num Calls, Avg, Min, Max, StdDev, Name.

> ⚠ Ловушка (интерактивный режим): последовательность `launch` → `start` → `stop` (или `shutdown`); `stop` НЕ завершает приложение, `cancel` НЕ сохраняет данные, `shutdown` принудительно закрывает CLI и отменяет активный сбор.
> ➕ Нюанс прав доступа: на кластерах сбор семплов CPU и некоторых данных может требовать разрешений ОС (`perf_event_paranoid`), а доступ к аппаратным счётчикам GPU (для ncu) может быть ограничен администратором — типичная ошибка `ERR_NVGPUCTRPERM` (нужны права/настройка драйвера, либо запуск от администратора). Проверить окружение помогает `nsys status -e`.

# ЧАСТЬ 5. Слайд 13 — «GPU Starvation Investigations» (расследование «голодания» GPU)

## Что на скриншоте

Окно Nsight Systems, таймлайн ~3.0–3.7 с:
- сверху **CPU (80)** — загрузка 80 логических ядер;
- **Threads (82)** — потоки процесса `python`: [419], [426], [364], [406]. У потоков подстроки: **OS runtime libraries**, **CUDA API**, **cuDNN**, **cuBLAS**, **Profiler overhead**;
- на длинных участках у главного потока — **`pthread_cond_wait`** (поток **ожидает условную переменную**, т.е. спит, пока другой поток не подготовит данные);
- ниже — **GPU «CUDA (Tesla P100-SXM2-16GB, …)»** → **Stream 70** → **Memory** и **Kernels**: `maxwell_fp16_scudnn_fp16…`, `EigenMetaKernel`, `bn_bw_1C11_kernel_new`, `dgrad_engine` и т.д.;
- **два красных прямоугольника** выделяют **пустые промежутки** на строке GPU, где ядер нет — **GPU простаивает**.

## Как читать картинку (логика расследования)

1. На GPU **нет ядер** на промежутке → «голодание».
2. Смотрим вверх, что в это время делает **CPU**: потоки в `pthread_cond_wait` / заняты чем-то не-CUDA (препроцессинг, чтение данных). Значит, **CPU не успевает подавать работу**, либо ждёт другой поток.
3. Когда CPU-поток закончил подготовку, он делает вызовы **CUDA API** (видны над ядрами), и GPU начинает считать (правая часть таймлайна — плотные ядра).

Вывод: **узкое место — не GPU, а CPU/конвейер подготовки данных.** Ускорять ядра бессмысленно.

## Названия ядер на скриншоте (для понимания контекста)

- **`maxwell_fp16_scudnn_fp16…`** — ядро cuDNN (свёртка в fp16, «scudnn» — свёрточные ядра из cuDNN).
- **`EigenMetaKernel`** — ядро библиотеки **Eigen** (типично для TensorFlow; поэлементные операции).
- **`bn_bw_1C11_kernel_new`** — cuDNN **batch normalization, backward** (`bw` = backward).
- **`dgrad_engine`** — cuDNN **gradient по данным (data gradient)** при обратном проходе свёртки.
- Видно, что это **обучение нейросети** (forward/backward).
- **Tesla P100-SXM2-16GB** — GPU архитектуры Pascal, 16 ГБ HBM2, форм-фактор SXM2 (NVLink).

## ➕ Причины GPU starvation и способы лечения

| Причина | Решение |
|---------|---------|
| Медленная загрузка/препроцессинг данных на CPU (чтение с диска, аугментации) | **Prefetching**, больше **worker-процессов** загрузчика данных (напр. `num_workers` в PyTorch DataLoader, `tf.data.prefetch`), кэширование, быстрые форматы данных |
| Последовательная работа «CPU подготовил → GPU посчитал → снова CPU» без перекрытия | **Конвейеризация (pipelining)**, двойная буферизация, асинхронные копирования в разных streams |
| Слишком маленькие ядра / много запусков, накладные расходы запуска (launch overhead ≈ единицы–десятки мкс на запуск) | **Объединение ядер (kernel fusion)**, **CUDA Graphs**, увеличение размера батча/работы на ядро |
| Лишние синхронизации (`cudaDeviceSynchronize`, `cudaStreamSynchronize`) | Убрать/ослабить синхронизации (следующий слайд) |
| Копирования не перекрываются с вычислением | **pinned memory**, `cudaMemcpyAsync` + streams |
| Блокирующие операции ввода-вывода | Асинхронный I/O, отдельные потоки |
| Нехватка параллелизма на CPU (Python GIL) | многопроцессность вместо потоков |

> ⚠ Ловушка: «GPU утилизация 100% по `nvidia-smi`» не гарантирует эффективность — `nvidia-smi` показывает долю времени, когда **хоть одно ядро исполнялось**, а не сколько SM реально занято. Для настоящей картины нужен таймлайн.

# ЧАСТЬ 6. Слайд 14 — «Unnecessary GPU Synchronization Calls» (лишние синхронизации)

## Что на скриншоте

Таймлайн в масштабе **миллисекунд** (≈ +197.395 … +197.478 мс на 51-й секунде):
- GPU: **TITAN X (Pascal)**, **Stream 13**; в разделе **Kernels** — ядро **`bn_fw_tr_1C11_kernel_new`** (**batch normalization forward training**), в **Memory → DtoD memcpy** — копирование **device→device** (`Memcpy`, красным).
- Строка **cuDNN:** вызов **`cudnnBatchNormalizationForwardTraining`** (красный блок) — именно он запускает ядро.
- Строка **CUDA API:** маленькие зелёные вызовы (запуск ядра), затем **длинный зелёный блок `cudaStreamSynchronize`**, потом **`cudaMemcpyAsync`** (красный), затем снова **`cudaStreamSynchronize`**.
- Синий блок на GPU (ядро) короче, чем период `cudaStreamSynchronize` на CPU.

## Что здесь не так (анализ)

- **`cudaStreamSynchronize` блокирует CPU-поток до завершения всех команд в stream.** CPU «стоит» (зелёный блок), хотя мог бы уже готовить и ставить в очередь следующие команды.
- Между завершением ядра и стартом копирования на GPU появляется **пробел** (GPU простаивает, т.к. следующую команду ещё не поставили в очередь — CPU только что вышел из синхронизации).
- Потом после `cudaMemcpyAsync` — **ещё одна синхронизация** — опять ожидание. Получается **«запуск → ожидание → запуск → ожидание»**, вместо **непрерывного потока команд** в очереди.
- Итог: теряется **асинхронность** (CPU и GPU работают по очереди, а не параллельно); накапливаются задержки запуска; GPU недогружен.

## Как лечить

- **Убирать синхронизации**, которые не нужны для корректности (не звать `cudaDeviceSynchronize` после каждого вызова). Синхронизировать только перед **использованием результата на хосте**.
- Для зависимостей между stream — использовать **события (`cudaEvent_t`, `cudaStreamWaitEvent`)** вместо блокирующего ожидания на CPU.
- Ставить в очередь **много команд подряд** (CPU «убегает вперёд» на глубину очереди), синхронизироваться редко.
- **Нюанс: неявная (implicit) синхронизация.** Некоторые вызовы синхронизируют неявно: `cudaMalloc`, `cudaFree`, `cudaMemcpy` (синхронный) с pageable-памятью, `cudaHostAlloc`, операции на **default (legacy) stream**, который синхронизируется с другими блокирующими streams. На таймлайне они выглядят как «длинные» вызовы API — их ищут.
- **Нюанс про асинхронные копирования:** `cudaMemcpyAsync` из **pageable** (обычной) памяти хоста в большинстве случаев ведёт себя **полусинхронно** (через временный staging-буфер) → нужна **pinned-память** (`cudaMallocHost`/`cudaHostAlloc`).
- **Нюанс про инструменты:** профайлер сам может влиять на поведение (особенно с включённой трассировкой) — важно сопоставлять с реальным временем без профайлера.

> ➕ Как это видно в nsys: строки «CUDA API» (длинные синхронизации) + строки «Streams» (пробелы между ядрами). Таблица `nsys stats` (cuda_api_sum) показывает, что **`cudaStreamSynchronize`/`cudaDeviceSynchronize` занимают большой % времени API** — признак проблемы (но часть этого времени — это просто честное ожидание длинного ядра, поэтому смотреть надо именно на промежутки на GPU).

# ЧАСТЬ 7. Слайд 15 — «NVIDIA Nsight Systems» (поддерживаемые модели программирования)

Пункты слайда и их смысл:

1. **Support: MPI, OpenACC, OpenMP.**
2. **Сложные возможности добычи данных (data mining)**, выходящие за пределы базовой статистики (доступ к данным через SQLite-экспорт, скрипты, expert system).
3. **Поддержка нескольких одновременных сессий** (`nsys sessions`).
4. **MPI trace:** анализ того, когда потоки **заняты** или **заблокированы** в долго выполняющихся функциях стандарта MPI. Доступно для **OpenMPI, MPICH и NVSHMEM**.
   - Видны `MPI_Send/Recv/Wait/Allreduce/Barrier`… и их длительность — можно найти **дисбаланс загрузки** между рангами (один ранг долго считает, остальные ждут на barrier/allreduce).
5. **OpenACC trace:** видно, **где код был перенесён (offload) и распараллелен на GPU**; помогает анализировать активность CPU и GPU, работающих параллельно.
   - Для директив `#pragma acc kernels/parallel/data` отображаются области: **compute construct**, **data region**, **enter/exit data**, **wait**, `update`, а также порождённые ядра и копирования.
6. **OpenMP trace:** доступен для компиляторов, поддерживающих **OpenMP 5** и интерфейс **OMPT** (OpenMP Tools Interface). Позволяет трассировать **параллельные регионы**, распределённые по **потокам CPU или на GPU** (offloading, `target`-регионы).
7. **CUDA Graphs:** помогает понять выполнение ядер и графов; ядра можно **«проследить» обратно** через запуск графа (graph launch — на слайде опечатка «lunch»), инстанцирование (instantiation) и вплоть до **создания узла** (node creation) — чтобы найти **происхождение исполнения ядра на GPU**.

## ➕ Пояснения

- **MPI** — модель передачи сообщений между процессами (ранками). **NVSHMEM** — PGAS-библиотека NVIDIA для обмена между GPU.
- **OMPT** — стандартный интерфейс OpenMP для инструментирования (колбэки на события: начало/конец параллельного региона, барьера, задач).
- **OpenACC** — директивная модель (`#pragma acc`). Для **простого профилирования** у PGI/NVIDIA HPC compiler есть переменная окружения **`NV_ACC_TIME=1`** (ранее `PGI_ACC_TIME=1`) — по завершении программа печатает таблицу времени в регионах и ядрах; информацию о том, что компилятор сделал с кодом, даёт `-Minfo=accel`. Для nsys: `nsys profile -t openacc,cuda ./app` (или `--trace=openacc,...`).
- **CUDA Graph** — заранее записанный граф зависимых операций (ядра, копирования), запускаемый **одним вызовом** `cudaGraphLaunch`. Уменьшает **накладные расходы запуска** (особенно при множестве коротких ядер) — это ответ на GPU starvation из-за launch overhead. Этапы: **создание графа** (capture через stream или явное создание узлов) → **инстанцирование** (`cudaGraphInstantiate`) → **запуск** (`cudaGraphLaunch`).

# ЧАСТЬ 8. Слайд 16 — «NVIDIA Nsight Compute (ncu)»: интерактивный профайлер CUDA-ядер

## Что на слайде

- **Interactive CUDA Kernel profiler.**
- **Targeted metric sections** (целевые секции метрик) для различных аспектов производительности (Debug/Profile); **отладка API** через пользовательский интерфейс и командную строку.
- **Очень высокочастотные GPU-счётчики производительности**, настраиваемый сбор и представление данных (таблицы, графики…).
- **Правила на Python** для «управляемого» анализа (guided analysis) или постобработки.
- Настраиваемый, управляемый данными интерфейс и сбор метрик; **расширяется скриптами анализа** для постобработки результатов.
- Ссылка: https://developer.nvidia.com/nsight-compute.

## Расшифровка

- **Sections (секции)** — наборы метрик, объединённые по теме. Основные:
  - **GPU Speed Of Light (SOL) Throughput** — «какой процент теоретического максимума» достигнут по вычислениям (SM) и по памяти. Главный индикатор: ядро **compute-bound** или **memory-bound**;
  - **Compute Workload Analysis** — загрузка конвейеров (FMA, ALU, Tensor…), IPC;
  - **Memory Workload Analysis** — трафик L1/L2/DRAM, hit rate, **bank conflicts** разделяемой памяти, коалесцирование (sectors per request);
  - **Scheduler Statistics / Warp State Statistics** — сколько warp готовы к исполнению, **причины простоя warp (stall reasons)**;
  - **Occupancy** — теоретическая и достигнутая заполняемость (лимитирует число регистров, shared memory, размер блока);
  - **Launch Statistics** — размер сетки/блока, регистры на поток, shared memory;
  - **Source Counters** — привязка метрик к строкам исходного кода и SASS-инструкциям.
- **Rules (правила)** — Python-скрипты, которые читают метрики и выдают **словесные рекомендации** («ядро ограничено пропускной способностью L2; рассмотрите…»), а также могут применяться при постобработке.
- **Командная строка:** `ncu` (профилирование и вывод в консоль/файл), **GUI:** `ncu-ui`.

## ➕ Критически важные нюансы работы ncu (частые «каверзные» вопросы)

1. **Replay (повторное воспроизведение):** аппаратных счётчиков на GPU **ограниченное число**, одновременно собрать все метрики нельзя. Поэтому ncu **запускает каждое профилируемое ядро несколько раз (passes)**, собирая в каждом проходе часть метрик. Перед каждым проходом **сохраняется и восстанавливается состояние памяти** — ядро должно быть воспроизводимым. Следствие: **профилирование ncu очень медленное** (замедление в десятки–сотни раз на ядро).
2. **Профилируют отдельные ядра, а не всю программу.** Выбирать нужно фильтрами: имя ядра (`-k`/`--kernel-name`), пропустить первые N запусков (`-s`/`--launch-skip`), ограничить число (`-c`/`--launch-count`), по NVTX-диапазонам (`--nvtx`, `--nvtx-include`).
3. **Времена ядер в ncu ≠ времена в nsys.** ncu по умолчанию **фиксирует частоты GPU** (clock control = base) и **сбрасывает кэши** между проходами (cache control = all) для воспроизводимости → длительности отличаются от «боевых». Для сравнения с реальной работой — смотреть время в nsys.
4. **Ядро в ncu исполняется сериализованно:** профилируемые ядра не перекрываются, поэтому ncu не показывает эффект перекрытия streams.
5. **Типичные команды:**

```bash
ncu ./app                              # базовый набор секций, вывод в консоль
ncu --set full -o profile ./app        # полный набор метрик → profile.ncu-rep
ncu -k my_kernel -s 5 -c 1 ./app       # только ядро my_kernel, пропустить 5 запусков, профилировать 1
ncu --section SpeedOfLight ./app       # только секция SOL
ncu --metrics sm__throughput.avg.pct_of_peak_sustained_elapsed ./app   # конкретная метрика
ncu --target-processes all ./mpirun_app   # для дочерних процессов (напр., MPI)
ncu-ui profile.ncu-rep                 # открыть отчёт в GUI
```

6. **Доступ:** для чтения аппаратных счётчиков нужны **права** (на кластерах бывает ограничено администратором) → ошибка `ERR_NVGPUCTRPERM`.
7. **Ключевые метрики для запоминания:**
   - **SM Throughput / Memory Throughput (% of peak)** — что ближе к 100%, то и лимитирует;
   - **Achieved Occupancy** vs **Theoretical Occupancy**;
   - **L1/L2 hit rate**;
   - **Global load/store efficiency** (коалесцирование);
   - **Warp divergence / branch efficiency** (расхождение ветвлений);
   - **Shared memory bank conflicts**;
   - **Warp stall reasons** (ожидание памяти, барьера, зависимости по данным и т.д.);
   - **Registers per thread** (много регистров → мало warp → низкая occupancy, возможен **register spilling**).

> ⚠ Ловушка: фраза «API debugging» в слайде не означает отладку логики ядра (поиск ошибок). Отладка корректности — **cuda-gdb**, **compute-sanitizer**; ncu — это именно **профайлер** (+ инспекция CUDA API вызовов).
> ⚠ Ловушка: ncu и nsys **не заменяют** друг друга: nsys — «широко и поверхностно» (время событий), ncu — «узко и глубоко» (счётчики ядра).

# ЧАСТЬ 10. Слайд 18 — «Nsight Compute Feature Spotlight in CUDA Toolkit 11 and A100»

## 10.1. Roofline Analysis (анализ по модели Roofline)

**Определения со слайда:**
- **Arithmetic intensity** (арифметическая интенсивность) = Compute/Memory — то есть **число операций / число байт**, перемещённых с памятью. Единица: **FLOP/byte**.
- **FLOPS** = Floating Point Operations per Second (операций с плавающей запятой в секунду).

> ⚠ Ловушка: на слайде «Compute/Memory» — условная запись. Точнее: **AI = FLOP / byte** (число операций на каждый байт, прочитанный/записанный в память устройства).

**Модель Roofline:**

```
Достижимая производительность = min( Пиковая производительность вычислений (FLOP/s),
                                     AI × Пиковая пропускная способность памяти (B/s) )
```

- На графике (лог-лог): ось X — арифметическая интенсивность (FLOP/byte), ось Y — производительность (FLOP/s).
- **Наклонная линия** («крыша памяти») — ограничение пропускной способностью памяти: слева — ядра **memory-bound**.
- **Горизонтальная линия** («крыша вычислений») — пик вычислений: справа — ядра **compute-bound**.
- **Точка пересечения («ridge point»)** — AI, при котором ограничение переходит с памяти на вычисления: `AI_ridge = Peak_FLOPS / Peak_Bandwidth`.
- Точка ядра на графике: расстояние до «крыши» показывает **запас оптимизации**. Если точка под наклонной линией — ядро упирается в память, нужно **увеличивать переиспользование данных** (shared memory, тайлинг, кэш). Если под горизонтальной — не хватает эффективности вычислений (низкая occupancy, расхождения, неэффективные инструкции).
- Для A100 (40 ГБ) пики примерно: **FP32 ≈ 19.5 TFLOP/s**, **пропускная способность HBM2 ≈ 1.5 ТБ/с** → ridge ≈ 12–13 FLOP/byte. (Ориентировочно, для понимания порядка величин.)

**Скриншот на слайде (что на нём):**
- Секция **GPU Speed Of Light Throughput**: Compute (SM) Throughput **86.42 %**; Memory Throughput **8.04 %**; L1/TEX Cache **8.45 %**; L2 Cache **0.97 %**; DRAM **0.24 %**; Duration ~1.14 мс.
- Блок **Bottleneck:** «Ядро использует более 80% доступной вычислительной или памяти производительности устройства. Для дальнейшего улучшения нужно переносить работу с наиболее загруженного блока на другой» — то есть ядро **compute-bound** (SM загружен на 86%, память почти не нагружена).
- Блок **Roofline Analysis:** «Отношение пиковой FP32 к FP64 производительности на устройстве — 32:1. Ядро достигло близко к 1% пиковой FP32-производительности и 0% FP64». На графике — «Floating Point Operations Roofline» с точками для single precision (AI = 72.30 FLOP/byte, производительность ≈ 114.9 GFLOP/s) и double.
- Всплывающая подсказка — «Single Precision Achieved Value».

**Нюансы:**
- Для каждого типа точности (FP32, FP64, Tensor) своя «горизонтальная крыша» — поэтому на графике несколько горизонтальных линий.
- Отношение FP32:FP64 зависит от GPU (у потребительских карт 32:1 или 64:1, у A100 — 2:1); в отчёте оно вычисляется для **конкретного устройства**.
- Высокая загрузка SM (86%) при малой доле пиковых FLOP/s может означать, что SM заняты **не-FP-инструкциями** (целочисленными, адресной арифметикой, и т.п.).

## 10.2. Asynchronous copy (асинхронное копирование, A100)

- Аппаратная возможность архитектуры **Ampere (A100)**: копирование **из глобальной памяти напрямую в разделяемую (shared)**, **минуя регистры и L1-путь «через регистровый файл»** (инструкции `cp.async`/LDGSTS; в CUDA C++ — `cuda::memcpy_async`, `__pipeline_memcpy_async`).
- Смысл: данные загружаются в shared memory **асинхронно**, пока SM выполняет вычисления на ранее загруженных данных → **перекрытие вычислений и загрузки** (программная конвейеризация/double buffering) без траты регистров на промежуточные значения.
- На скриншоте красной стрелкой отмечена на диаграмме памяти связь, показывающая объём асинхронных копирований (на скриншоте **0.00 B** — ядро их не использовало). Nsight Compute теперь **показывает трафик, созданный async copy**, в Memory Chart.

## 10.3. Sparse Data Compression (сжатие данных; нюанс A100)

- Слайд: показывает **объём данных, сжатых этой функцией, и коэффициент сжатия**; помогает с ядрами, у которых проблемы с **пропускной способностью или кэшем**.
- Суть: в A100 есть **аппаратное сжатие данных на уровне L2-кэша** (compute data compression) — может уменьшить трафик к DRAM для данных с большим количеством нулей/повторяющихся значений («разреженных», sparse). Требует выделения памяти с поддержкой сжатия (CUDA API для compressible memory).
- На скриншоте (Memory Chart): блок **L2 Compression, Ratio: 4.00**; потоки данных **665.39 MB / 166.35 MB** (до/после сжатия: 665.39 / 166.35 ≈ 4.0) — то есть данные сжаты в 4 раза.
- Другие данные на диаграмме: **L1/TEX Cache Hit Rate 74.81 %**, **L2 Cache Hit Rate 67.37 %**, обмен с **Device Memory** 126.02 MB / 131.32 MB, **Shared Memory**.

> ➕ **Memory Chart (диаграмма памяти)** — один из главных видов ncu: блоки Kernel → L1/TEX → Shared Memory → L2 → Device Memory (DRAM), стрелки с объёмом данных и hit rate. Ищем: куда уходит трафик, где низкий hit rate, лишние обращения к DRAM.
> ⚠ Не путать **структурную разреженность (2:4 sparsity)** тензорных ядер A100 (аппаратное ускорение матричных операций) и **сжатие данных в L2** — на слайде речь о втором (экономия пропускной способности).

# ЧАСТЬ 11. Слайды 19–20 — «NVIDIA® Tools Extension SDK (NVTX)»

## 11.1. Слайд 19: что такое NVTX

- **C-based API** для **аннотирования событий, диапазонов кода и ресурсов** в приложении.
- Программы с NVTX могут использовать **NVIDIA Nsight, Tegra System Profiler и Visual Profiler**, чтобы **захватывать и визуализировать** эти события и диапазоны.
- Зачем: профайлер видит вызовы CUDA и ядра, но **не знает вашу логику** («этап подготовки данных», «итерация 5», «слой свёртки»). NVTX-метки добавляют **смысловую разметку** на таймлайн — удобно искать, к какому участку кода относятся простои.

**Скриншот терминала (`ncu -h | grep nvtx`):** опции ncu для NVTX:

| Опция | Смысл |
|-------|-------|
| `--nvtx` | включить поддержку NVTX |
| `--nvtx-include arg` | добавить условие **включения** в NVTX-фильтр (выбор ядер для профилирования) |
| `--nvtx-exclude arg` | добавить условие **исключения** |
| `--print-nvtx-rename arg (=none)` | как использовать NVTX для переименования (`per-nvtx`) |

Примеры использования:
```bash
ncu --nvtx --nvtx-include "Domain A@Range A"            # диапазон «Range A» в домене «Domain A»
ncu --nvtx --nvtx-exclude "Range A]"                    # исключить (синтаксис со скобками уточняет вложенность)
ncu --nvtx --nvtx-include "Range A" --nvtx-exclude "Range B"  # внутри A, но не внутри B
```
Формат фильтра: `Домен@Диапазон`; скобки `[`/`]` в имени уточняют положение диапазона в стеке вложенных диапазонов (точный синтаксис — в `ncu -h` / документации). **Без `--nvtx` фильтры не работают.**

## 11.2. Слайд 20: пример кода

```c
#include <nvToolsExt.h>
#include <sys/syscall.h>
#include <unistd.h>

static void wait(int seconds) {
    nvtxRangePush(__FUNCTION__);      // начать диапазон с именем функции
    nvtxMark("Waiting...");           // мгновенная метка-событие
    sleep(seconds);
    nvtxRangePop();                   // закончить диапазон
}

int main(void) {
    nvtxNameOsThread(syscall(SYS_gettid), "Main Thread");  // дать имя потоку ОС
    nvtxRangePush(__FUNCTION__);
    wait(1);
    nvtxRangePop();
}
```

**Разбор функций:**

| Функция | Что делает | Нюанс |
|---------|-----------|-------|
| `nvtxRangePush(name)` | открывает **вложенный диапазон** в текущем потоке (стек); возвращает уровень вложенности | Должен быть **парный** `nvtxRangePop()` **в том же потоке**; диапазоны вложенные (как скобки) |
| `nvtxRangePop()` | закрывает последний открытый диапазон потока | Возвращает уровень вложенности (или отрицательное при ошибке) |
| `nvtxRangeStartEx` / `nvtxRangeStart` + `nvtxRangeEnd(id)` | диапазон **с идентификатором**, который можно начать в одном потоке, а закончить в другом; не обязан быть вложенным | Для асинхронных/пересекающихся диапазонов |
| `nvtxMark(msg)` / `nvtxMarkEx` | **точечное** событие (метка без длительности) | Отображается как отметка на таймлайне |
| `nvtxNameOsThread(tid, name)` | задаёт **имя потоку ОС** по его идентификатору | `syscall(SYS_gettid)` — получение **TID** потока в Linux (а не `pthread_self`); именно поэтому в примере подключены `<sys/syscall.h>` и `<unistd.h>` |
| `__FUNCTION__` | макрос компилятора: имя текущей функции | Удобно автоматически называть диапазон |

- **Ex-версии** (`nvtxRangePushEx`, `nvtxMarkEx`) принимают структуру `nvtxEventAttributes_t` — можно задать **цвет**, категорию, payload, тип сообщения (ASCII/Unicode).
- **Домены (domains)** — способ разделить аннотации разных библиотек/модулей (`nvtxDomainCreate`), чтобы имена не пересекались (отсюда формат `Domain@Range` в ncu).
- **Накладные расходы:** NVTX очень лёгкий; **если профайлер не подключён, вызовы NVTX практически ничего не делают** (no-op) — можно оставлять в продакшн-коде. Сборка: в старых версиях линковали `-lnvToolsExt`; в **NVTX v3** (header-only) библиотека подгружается динамически и нужен `-ldl`. (Детали зависят от версии CUDA Toolkit.)
- В фреймворках: PyTorch (`torch.cuda.nvtx.range_push/pop`), TensorFlow, Python-пакет `nvtx` — аннотации слоёв/итераций.

## 11.3. Команды на слайде

```bash
nsys profile -t nvtx --stats=true …
# Для кода на Julia:
nsys profile -t nvtx,cuda -o output_file.qdrep julia --project=../../ script.jl
```

- `-t nvtx` — трассировать только NVTX-события; `-t nvtx,cuda` — NVTX **и** CUDA API/ядра (список через запятую без пробелов).
- `--stats=true` — вывести сводную статистику; в ней появится таблица **NVTX Range Summary** (время в каждом диапазоне, число вызовов).
- `-o output_file.qdrep` — выходной файл. **`.qdrep` — формат старых версий Nsight Systems; в современных — `.nsys-rep`.** Если указать расширение вручную, актуальные версии могут его заменить на `.nsys-rep`.
- **Julia:** запуск через `nsys profile … julia …` — профилируется сам процесс Julia; для аннотаций в коде Julia используют пакет **NVTX.jl**; для GPU-кода — **CUDA.jl** (трассировка CUDA включается `cuda` в `-t`).
- Ссылка: https://docs.nvidia.com/nsight-visual-studio-edition/nvtx/index.html

> ⚠ Ловушка: `nvtxRangePush` и `nvtxRangePop` — **на одном потоке и строго парно**. Забытый `Pop` ломает вложенность и искажает таймлайн.
> ⚠ Ловушка: `nvtxMark` — не диапазон, а **мгновенная отметка**.
> ⚠ Ловушка: `nvtxNameOsThread` принимает **TID потока ОС**, а не `pthread_t`; на Linux его получают через `syscall(SYS_gettid)` (в glibc ≥ 2.30 есть `gettid()`).
> ⚠ Ловушка: слайд упоминает «Visual Profiler» — nvvp устарел (см. Часть 1), актуальные потребители NVTX — Nsight Systems и Nsight Compute.

# ЧАСТЬ 13. Дополнительные нюансы (то, о чём любят спрашивать)

## 13.1. nsys vs ncu: сравнение

| Критерий | **Nsight Systems (nsys)** | **Nsight Compute (ncu)** |
|----------|---------------------------|--------------------------|
| Масштаб | вся программа, система целиком (CPU+GPU+OS) | отдельные CUDA-ядра |
| Вопрос | «**Где** и **когда** тормозит?» | «**Почему** это ядро медленное?» |
| Данные | таймлайн, трассировка API, семплирование CPU, обмен данными | аппаратные счётчики, метрики, исходный код/SASS |
| Накладные расходы | низкие | высокие (replay, много проходов) |
| Типичный результат | видим простои GPU, лишние синхронизации, плохое перекрытие, дисбаланс MPI | видим memory-bound/compute-bound, коалесцирование, bank conflicts, occupancy, stall reasons |
| Формат отчёта | `.nsys-rep` (раньше `.qdrep`), SQLite | `.ncu-rep` |
| CLI / GUI | `nsys` / `nsys-ui` | `ncu` / `ncu-ui` |
| Порядок использования | **первым** | **вторым**, на «горячих» ядрах |

## 13.2. Compute-bound vs memory-bound vs latency-bound

- **Memory-bound:** ограничение — пропускная способность памяти (SOL Memory ≫ SOL Compute; точка под наклонной частью roofline). Лечение: коалесцирование, shared memory/тайлинг, сжатие, меньше типов данных (fp16 вместо fp32), слияние ядер.
- **Compute-bound:** ограничение — вычислительные блоки (SOL Compute высокий). Лечение: меньше инструкций, быстрые встроенные функции, tensor cores, FMA, меньший тип точности.
- **Latency-bound:** оба показателя низкие (всё «недогружено») — мало параллелизма, низкая occupancy, расхождения, зависимости; лечение: больше потоков/блоков, меньше регистров, ILP.
- **Launch/CPU-bound (видно в nsys):** ядра короткие, между ними пробелы — накладные расходы запуска/CPU; лечение: CUDA Graphs, слияние ядер.

## 13.3. Как отличить проблемы на таймлайне nsys

| Что видно | Диагноз |
|-----------|---------|
| Большие пробелы между ядрами в stream, CPU занят/в ожидании чем-то ещё | GPU starvation (проблема подачи работы) |
| Длинные `cudaStreamSynchronize`/`cudaDeviceSynchronize`, за которыми пробелы | лишняя синхронизация |
| Копирования и ядра идут строго друг за другом, хотя могли бы параллельно | нет перекрытия (нужны streams + pinned memory) |
| Много очень коротких ядер с пробелами | накладные расходы запуска (launch overhead) |
| Копирование HtoD/DtoH занимает основную долю времени | PCIe/NVLink — узкое место, надо уменьшать передачи |
| Ранги MPI ждут в `MPI_Wait/Barrier/Allreduce`, один ранг ещё считает | дисбаланс нагрузки |
| Копирование из pageable-памяти выглядит синхронным | нужна pinned-память |
| Вызовы `cudaMalloc/cudaFree` внутри цикла | неявные синхронизации и накладные расходы: выделять память один раз |

## 13.4. Общие рекомендации по методике

- Профилировать **релизную (оптимизированную) сборку** с `-O2/-O3`; для привязки к исходному коду — `-lineinfo` (nvcc) — не меняет оптимизацию, но добавляет информацию о строках.
- Делать **прогревочный запуск** (JIT, ленивая инициализация CUDA-контекста, первый запуск cuDNN autotune) — первая итерация заведомо медленнее и «портит» картину.
- Профилировать **ограниченный участок** (несколько итераций), иначе отчёт огромный. Для этого: NVTX-диапазоны, `--capture-range`, `--duration`, `cudaProfilerStart/Stop`.
- Сравнивать **до/после** на одинаковых данных и конфигурации; повторять измерения (шум).
- Не забывать, что **профайлер влияет на программу** — особенно ncu (сериализация ядер, сброс кэшей, фиксированные частоты).
- Для кластеров (SLURM и т.п.) запуск идёт через планировщик, отчёт потом копируют на локальную машину и открывают в `nsys-ui`/`ncu-ui` (GUI может работать **на другой ОС**, в том числе macOS — поэтому на слайде «MacOSX (host only)»).

# ЧАСТЬ 15. Вопросы для самопроверки (с ответами)

1. **Какие инструменты заменили nvprof и nvvp?** — Nsight Systems (`nsys`) для уровня приложения/таймлайна и Nsight Compute (`ncu`) для метрик ядер.
2. **С какого инструмента начинают профилирование и почему?** — С Nsight Systems: низкие накладные расходы, видна вся картина; затем «ныряют» в самые тяжёлые ядра через Nsight Compute.
3. **Для чего Nsight Graphics?** — Отладка и оптимизация графических нагрузок (кадры, шейдеры).
4. **Что такое GPU starvation?** — Простой GPU из-за того, что ему не подают работу вовремя (медленный CPU, ожидание данных, синхронизации, launch overhead).
5. **Как GPU starvation выглядит на таймлайне?** — Пробелы между ядрами на строке GPU/stream, при этом CPU-потоки заняты другим или ждут (например, `pthread_cond_wait`).
6. **Какие 4 проблемы по слайду 10 находит Nsight Systems?** — GPU starvation; недостаточная параллелизация/конвейеризация на CPU; неожиданно дорогой алгоритм CPU/GPU; лишняя синхронизация GPU.
7. **Чем tracing отличается от sampling?** — Tracing фиксирует каждое событие; sampling периодически снимает состояние (стек) и даёт статистику.
8. **Как профайлер корректно показывает «где CPU ждёт»?** — Состояние потока (Blocked State/OS runtime: `pthread_cond_wait`, мьютексы, fence) и вызовы синхронизации в строке CUDA API.
9. **Чем плох `cudaStreamSynchronize` после каждой операции?** — Блокирует CPU, обрывает конвейер команд, создаёт пробелы на GPU, разрушает перекрытие CPU/GPU.
10. **Назовите неявно синхронизирующие вызовы.** — `cudaMalloc`, `cudaFree`, синхронный `cudaMemcpy`, `cudaHostAlloc`, операции на default stream.
11. **Что даёт pinned-память для копирований?** — Более быстрые передачи и настоящую асинхронность `cudaMemcpyAsync` (перекрытие с вычислениями).
12. **Что делает `nsys profile`?** — Запускает приложение и собирает отчёт за один шаг, параметры определяют, что и когда собирать.
13. **Чем `stop` отличается от `cancel` и `shutdown`?** — `stop` завершает сбор и сохраняет данные, приложение продолжает работать; `cancel` отбрасывает собранное; `shutdown` отключает и завершает CLI, активный сбор отменяется.
14. **Для чего `nsys stats` и `nsys analyze`?** — `stats` — сводные статистические таблицы из `.nsys-rep`/SQLite; `analyze` — отчёт экспертной системы с подсказками.
15. **Что делает `nsys export`?** — Экспортирует `.nsys-rep` в другие форматы (SQLite и т.д.).
16. **Что делают `status` и `sessions`?** — `status` — состояние сбора/пригодность окружения; `sessions` — информация о всех сессиях в системе.
17. **Для чего флаг `-t`?** — Список трассируемых API (`cuda,nvtx,osrt,mpi,openacc,…`).
18. **Что даёт `--stats=true`?** — Выводит сводную статистику после запуска.
19. **Что собирает MPI trace и для каких реализаций доступен?** — Время в функциях MPI (занят/заблокирован поток); OpenMPI, MPICH, NVSHMEM.
20. **Что нужно для трассировки OpenMP в nsys?** — Компилятор с поддержкой OpenMP 5 и интерфейса OMPT.
21. **Что даёт поддержка CUDA Graphs в nsys?** — Возможность проследить ядро обратно до запуска графа, инстанцирования и создания узла.
22. **Что такое Nsight Compute?** — Интерактивный профайлер CUDA-ядер со сбором аппаратных метрик, секциями, правилами на Python, GUI и CLI.
23. **Почему ncu запускает ядро несколько раз?** — Аппаратных счётчиков мало; метрики собираются по частям в нескольких проходах (replay).
24. **Почему время ядра в ncu отличается от nsys?** — ncu фиксирует частоты, сбрасывает кэши, сериализует ядра и добавляет накладные расходы.
25. **Как профилировать только нужное ядро?** — `ncu -k <имя> -s <пропуск> -c <число>`; или фильтры NVTX.
26. **Что такое Baseline в ncu?** — Закреплённый отчёт для сравнения с последующими (дельты метрик).
27. **Что такое Speed Of Light?** — Достигнутый процент теоретического пика по вычислениям и памяти; показывает, что лимитирует ядро.
28. **Что такое arithmetic intensity и в чём измеряется?** — Отношение числа операций к числу перемещённых байт; FLOP/byte.
29. **Как читать Roofline?** — Под наклонной частью — memory-bound, под горизонтальной — compute-bound; расстояние до «крыши» — запас оптимизации; ridge point = пик FLOPS / пик bandwidth.
30. **Что показывает Roofline-график на слайде?** — Ядро с AI ≈ 72 FLOP/byte и ≈ 115 GFLOP/s FP32 (около 1% пика), SM загружен на 86% — ядро compute-bound.
31. **Что такое asynchronous copy в A100?** — Копирование global → shared напрямую, минуя регистры, асинхронно относительно вычислений (`cp.async`).
32. **Что такое Sparse Data Compression в слайде?** — Сжатие данных на уровне L2 в A100; в отчёте показывается объём сжатых данных и коэффициент (на скриншоте 4.00).
33. **Что такое NVTX?** — C API для аннотирования диапазонов, меток и ресурсов в приложении, чтобы они отображались в профайлерах.
34. **Чем `nvtxRangePush/Pop` отличается от `nvtxRangeStart/End`?** — Push/Pop — вложенные диапазоны в одном потоке (стек); Start/End — диапазоны по идентификатору, могут начинаться и заканчиваться в разных потоках.
35. **Что делает `nvtxMark`?** — Ставит мгновенную метку-событие на таймлайне.
36. **Зачем `nvtxNameOsThread(syscall(SYS_gettid), "Main Thread")`?** — Дать читаемое имя потоку ОС в профайлере; нужен Linux TID.
37. **Как включить NVTX-фильтр в ncu?** — `--nvtx` + `--nvtx-include`/`--nvtx-exclude`; формат `Domain@Range`.
38. **Как профилировать Julia-скрипт?** — `nsys profile -t nvtx,cuda -o имя julia --project=… script.jl`.
39. **Расширение отчёта nsys в старых и новых версиях?** — `.qdrep` → `.nsys-rep`.
40. **Какие платформы поддерживает Nsight Systems?** — Linux, Windows; x86-64, Tegra, Power; macOS только как host (GUI).
41. **Что показывает «Blocked State» на последнем слайде?** — Время, когда поток CPU заблокирован (например, `CommandQueue::WaitForFence`).
42. **Что такое bottom-up view?** — Таблица семплов CPU, сгруппированная по функциям с наибольшим собственным временем (Self %).
43. **Что делать, если ядро memory-bound?** — Коалесцирование, shared memory/тайлинг, меньший тип данных, слияние ядер, сжатие.
44. **Можно ли в ncu увидеть перекрытие ядер в разных streams?** — Нет, ядра профилируются сериализованно; перекрытие смотрят в nsys.
45. **Какой профайлер использовать для поиска дисбаланса нагрузки между MPI-рангами?** — Nsight Systems с MPI-трассировкой.
46. **Чем `-lineinfo` полезен при профилировании?** — Позволяет привязать метрики к строкам исходного кода, не отключая оптимизации.
47. **Как ограничить сбор участком кода?** — `cudaProfilerStart/Stop` + `--capture-range=cudaProfilerApi`, либо NVTX-диапазон, либо `--delay/--duration`.
48. **Что такое launch overhead и как с ним бороться?** — Фиксированные накладные расходы на запуск ядра; CUDA Graphs, слияние ядер, больше работы на ядро.
49. **Что лучше для сравнения времени «как в жизни» — nsys или ncu?** — nsys (минимальное вмешательство, реальные частоты).
50. **Что за «Tesla P100-SXM2-16GB» и «TITAN X (Pascal)» на скриншотах?** — GPU архитектуры Pascal (P100 — серверная с NVLink и HBM2; TITAN X — потребительская).

# ЧАСТЬ 16. Мини-шпаргалка для повторения в последний момент

- **Nsight Systems = «где/когда»** (таймлайн, система целиком, `nsys`, `.nsys-rep`); **Nsight Compute = «почему»** (метрики ядра, `ncu`, `.ncu-rep`); **Nsight Graphics = кадры/шейдеры**.
- **nvprof/nvvp — устарели**; nvprof → `nsys profile` (+ `ncu` для метрик).
- **Цикл:** nsys → найти узкое место → ncu по самому тяжёлому ядру → исправить → снова nsys → пока не устроит.
- **Проблемы nsys:** GPU starvation, мало параллелизма/конвейеризации на CPU, дорогой алгоритм, лишняя синхронизация.
- **CLI-команды:** `profile`, `start`, `stop`, `cancel`, `launch`, `shutdown`, `export`, `stats`, `analyze`, `status`, `sessions`.
- **Поддержка:** MPI (OpenMPI, MPICH, NVSHMEM), OpenACC, OpenMP 5 (OMPT), CUDA Graphs.
- **ncu:** replay (несколько проходов), секции, Python-правила, baseline-сравнение, фильтры ядер, времена отличаются от nsys.
- **Roofline:** AI = FLOP/byte; min(пик вычислений, AI × bandwidth); наклон — memory-bound, горизонталь — compute-bound.
- **A100:** asynchronous copy (global → shared без регистров), сжатие данных в L2 (ratio 4.00 на слайде).
- **NVTX:** `nvtxRangePush/Pop` (вложенные, один поток), `nvtxMark` (метка), `nvtxNameOsThread(TID, имя)`; в ncu — `--nvtx --nvtx-include/--nvtx-exclude`; в nsys — `-t nvtx`.
- **Расширения отчётов:** `.qdrep` (старое) → `.nsys-rep`.
