# ЧАСТЬ 0. Введение и общие понятия (слайд 1)

## 0.1. Что сказано на слайде 1

- **Проблема:** разработка параллельного кода «с нуля» подвержена ошибкам синхронизации, **состояниям гонки (race conditions)** и **дедлокам**.
- **Решение — Algorithmic Skeletons (алгоритмические скелеты):** набор универсальных высокоуровневых шаблонов параллельной обработки (паттернов).
- Перечень паттернов: **Map**, **Reduce**, **Scan / Prefix Sum**, **Stencil**, **Histogram & Scatter/Gather**, **Matrix Tiling / GEMM**.

**Идея:** большинство параллельных задач — это композиция небольшого числа типовых паттернов, для каждого из которых известны **эффективная реализация, оценка сложности и узкие места**. Знание паттернов = умение не изобретать всё заново (и использовать готовые библиотеки: **Thrust, CUB, cuBLAS, CUTLASS**).

## 0.2. Базовая терминология анализа параллельных алгоритмов (нужна для всех слайдов)

| Термин | Смысл |
|--------|-------|
| **Work (работа), W** | суммарное число операций алгоритма (время на одном процессоре) |
| **Span / Depth (глубина), S** | длина самой длинной цепочки зависимых операций (время на бесконечном числе процессоров) |
| **Параллелизм** | отношение W / S — сколько операций «в среднем» можно делать одновременно |
| **Work-efficient (эффективный по работе)** | W параллельного алгоритма имеет тот же порядок, что и у лучшего последовательного (напр., O(N) для scan и reduce) |
| **Теорема Брента** | время на p процессорах: T_p ≤ W/p + S |
| **Memory-bound** | время определяется пропускной способностью памяти (мало FLOP на байт) |
| **Compute-bound** | время определяется вычислительными блоками |
| **Арифметическая (операционная) интенсивность** | число FLOP на байт, перемещённый с DRAM (FLOP/byte) |
| **Coalescing (коалесцирование)** | объединение обращений 32 потоков варпа к соседним адресам в минимум транзакций памяти |
| **Warp divergence** | потоки одного варпа идут по разным ветвям → ветви исполняются последовательно с маскированием |
| **Bank conflict** | несколько потоков варпа обращаются к *разным* адресам одного банка shared memory → сериализация |
| **Race condition** | результат зависит от порядка выполнения потоков при неатомарном доступе к общим данным |

➕ **Ключевая идея всей презентации:** на GPU почти всё упирается в **иерархию памяти** (DRAM → L2 → L1/Shared → регистры → Tensor Cores). Паттерны — это способы **уменьшить трафик к DRAM и избежать конфликтов/простоев**.

# ЧАСТЬ 1. Паттерн MAP (слайды 2–8)

## 1.1. Слайд 2 — Map: поэлементные преобразования

**Математическая формулировка:**

```
y_i = f(x_i)       или       z_i = f(x_i, y_i),       ∀ i ∈ [0, N−1]
```

- Суть: **независимое применение чистой функции к каждому элементу** входа.
- **Чистая функция (pure function):** результат зависит только от аргументов, нет побочных эффектов.
- **Класс задачи: Embarrassingly Parallel (идеальный параллелизм):**
  - нет зависимостей по данным между итерациями;
  - не нужна межпоточная синхронизация (`__syncthreads()` не нужен);
  - не нужны атомики (`atomicAdd` не нужен).
- Примеры: **AXPY** (`y = a·x + y`, поэлементное сложение векторов со скалярным множителем), **функции активации** в глубоком обучении (**ReLU, GELU, Sigmoid**), **точечная обработка изображений** (гамма-коррекция, пороговая фильтрация).

➕ **Нюансы:**
- Work = O(N), Span = O(1) (в идеале все N элементов параллельно).
- **Map почти всегда memory-bound:** например, `y = 2x` — 1 FLOP на 8 байт (чтение 4 + запись 4) → интенсивность ≈ 0,125 FLOP/B, далеко левее «ridge point». Поэтому **скорость Map = пропускная способность памяти**; вычислительные оптимизации бессмысленны, важны **коалесцирование, векторизация, слияние ядер (kernel fusion)**: последовательность Map-ядер (bias + ReLU + scale) выгодно слить в одно, чтобы данные читались из DRAM один раз.
- Map отличается от **Stencil** (нужны соседи) и от **Gather/Scatter** (индексы нерегулярные).

## 1.2. Слайд 3 — Наивная реализация Map в CUDA

```cuda
__global__ void naiveMapKernel(const float* __restrict__ in,
                               float* __restrict__ out, int N) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < N) out[idx] = in[idx] * 2.0f;   // произвольная f(x)
}
// запуск:
dim3 block(256);  dim3 grid((N + 255) / 256);   // округление вверх
```

- Подход: **«1 элемент = 1 аппаратная нить»**.
- `grid = (N + 255)/256` — целочисленное **округление вверх**; последний блок может быть неполным → защита `if (idx < N)`.
- `__restrict__` — обещание компилятору, что указатели **не пересекаются (no aliasing)** → можно агрессивнее переупорядочивать загрузки/использовать read-only кэш. `const` — только чтение.

**Проблемы наивного подхода по слайду:**
1. Жёсткая привязка конфигурации запуска к размеру N: если N превышает лимит сетки (для старых архитектур или 2D/3D), код падает.
2. Накладные расходы планировщика при частых запусках на массивах разного размера.
3. Хвостовой блок простаивает из-за проверки `if (idx < N)`.

> ⚠ **Ловушка (честная оценка слайда):** формулировки преувеличены. На современных GPU `gridDim.x` может быть до **2³¹ − 1** блоков, а `gridDim.y/z` — до **65 535**; «падение» возможно только для очень больших N или при неудачном использовании y/z-измерений. Реальные причины предпочесть grid-stride: **независимость ядра от N**, возможность **подобрать размер сетки под число SM**, **амортизация накладных расходов на создание/инициализацию потоков**, удобство отладки и **накопление значений в регистре** (важно для Reduce). Для простого Map наивная версия почти так же быстра — она упирается в пропускную способность памяти.

## 1.3. Слайд 4 — Grid-Stride Loop

```cuda
__global__ void gridStrideMapKernel(const float* __restrict__ in,
                                    float* __restrict__ out, int N) {
    int tid    = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = blockDim.x * gridDim.x;          // общее число нитей в сетке
    for (int i = tid; i < N; i += stride)
        out[i] = in[i] * 2.0f;
}
```

- **Идея:** нить обрабатывает не один элемент, а **шагает по массиву с шагом, равным общему числу нитей сетки**: `stride = blockDim.x × gridDim.x`.
- Нить `t` обрабатывает элементы `t, t+stride, t+2·stride, …`.
- **Все нити сетки двигаются «синхронным фронтом»**: на каждой итерации соседние нити читают соседние адреса → **коалесцированный доступ сохраняется**.

🧮 **Пример:** N = 10, сетка 2 блока × 2 нити (stride = 4). Нить 0: элементы 0, 4, 8; нить 1: 1, 5, 9; нить 2: 2, 6; нить 3: 3, 7.

> ⚠ **Ловушка:** если вместо этого дать каждой нити **непрерывный кусок** (`i = tid*chunk … (tid+1)*chunk`), соседние нити на одной итерации читают адреса, отстоящие на `chunk` → **некоалесцированный доступ**. Для GPU правильно «чередование» (как в grid-stride), для CPU — наоборот (непрерывные куски).
> ⚠ Тип индекса: при N > 2³¹ нужен `size_t`/`long long`, иначе переполнение `int`.

## 1.4. Слайд 5 — Преимущества Grid-Stride Loop

1. **Масштабируемость и независимость от оборудования:**
   - `num_blocks = num_SMs × (блоков на SM для скрытия задержек)` — размер сетки фиксируют исходя из числа мультипроцессоров;
   - код корректно работает для **любого N** (от 10 до миллиардов) без пересчёта конфигурации.
2. **Переиспользование ресурсов и аппаратный планировщик:** нити уже созданы и распределены по SM; накладные расходы запуска амортизируются; улучшается локальность L1/L2 при последовательных итерациях.
3. **Отладка и верификация:** ядро тестируют последовательно, запустив `<<<1, 1>>>` — один поток обходит весь массив (получаем «эталонный» последовательный результат); нет риска выйти за лимиты размерности сетки.

➕ **Как получить число SM и подобрать сетку:**
```cuda
int dev, numSMs;  cudaGetDevice(&dev);
cudaDeviceGetAttribute(&numSMs, cudaDevAttrMultiProcessorCount, dev);
int blocksPerSM;  // сколько блоков одновременно помещается на SM (по регистрам/shared)
cudaOccupancyMaxActiveBlocksPerMultiprocessor(&blocksPerSM, kernel, 256, 0);
int grid = numSMs * blocksPerSM;
```
Или `cudaOccupancyMaxPotentialBlockSize` — подсказывает размер блока и сетки.
➕ Побочный эффект: если работа по элементам **неравномерна**, grid-stride даёт лучшее выравнивание нагрузки между нитями (динамически нет, но статически «пересыпается» равномерно).

## 1.5. Слайд 6 — Векторизованный доступ к памяти

- Инструкции загрузки умеют считывать **за одну инструкцию 32, 64 или 128 бит на нить** (в SASS — `LDG.E.128`).
- Для `float` (32 бит) нить запрашивает 4 байта. **Векторизация:** объединяем 4 `float` в один `float4` (16 байт = 128 бит).
- Эффект:
  - **в 4 раза меньше инструкций** load/store;
  - более плотная утилизация конвейера памяти SM;
  - ближе к «потолку» пропускной способности DRAM.

➕ Нюансы: векторизация эффективна, если ядро упирается в **количество инструкций/запросов**, а не уже насыщает DRAM. Для очень простых ядер и больших N выигрыш обычно 5–20 %, но не «в 4 раза» по времени (слайд говорит про число инструкций). Типы: `float2/float4`, `int2/int4`, `double2` (16 байт), `uint4`.

## 1.6. Слайд 7 — Реализация векторизованного Map

```cuda
__global__ void vectorizedMapKernel(const float* __restrict__ in,
                                    float* __restrict__ out, int N) {
    const float4* in_vec  = reinterpret_cast<const float4*>(in);
    float4*       out_vec = reinterpret_cast<float4*>(out);
    int num_vectors = N / 4;
    int tid = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = blockDim.x * gridDim.x;
    for (int i = tid; i < num_vectors; i += stride) {
        float4 v = in_vec[i];
        v.x *= 2.0f; v.y *= 2.0f; v.z *= 2.0f; v.w *= 2.0f;
        out_vec[i] = v;
    // ... (на слайде код обрезан)
```

- `reinterpret_cast<const float4*>` — переинтерпретация указателя без копирования.
- `num_vectors = N / 4` — число 16-байтовых векторов.

> ⚠ **Ловушка (важно!):** при `N % 4 != 0` остаются **«хвостовые» элементы** (последние `N % 4`). В полном коде нужен **хвостовой цикл** обработки скалярами (например, поток с `tid < N % 4` обрабатывает элементы `4*num_vectors + tid`). На слайде код обрезан и хвост не показан.

## 1.7. Слайд 8 — Инженерные требования к векторизации

1. **Выравнивание (Alignment):**
   - для 128-битной транзакции адрес должен быть **кратен 16 байтам**;
   - `cudaMalloc` гарантирует выравнивание **минимум 256 байт** (безопасно);
   - осторожно со смещениями: `ptr + offset` (особенно нечётный/некратный 4 `offset` для `float`) может **нарушить выравнивание**;
   - невыровненный `reinterpret_cast` приведёт к потере производительности или **аппаратному исключению**.
2. **Баланс регистрового файла:** `float4` требует 4 регистров; при сложной f(x) и множестве локальных переменных возможен **Register Spilling** (вытеснение регистров в локальную память = медленная DRAM/L1).
3. **Чек-лист идеального Map-ядра:**
   1. Коалесцированный доступ;
   2. Grid-Stride Loop;
   3. Векторизация загрузок до 128 бит (`float4/int4`);
   4. Модификатор `__restrict__`.

> ➕ На практике невыровненный доступ к `float4` вызывает ошибку **`misaligned address`** (`cudaErrorMisalignedAddress`), а не «просто медленно». Если выравнивание не гарантировано — использовать скалярный путь для «головы» массива.
> ➕ Регистры: `-maxrregcount`, `__launch_bounds__` управляют числом регистров. Spill виден в `nvcc -Xptxas -v` (строки «spill stores/loads»).

# ЧАСТЬ 2. Паттерн REDUCE (слайды 9–17)

## 2.1. Слайд 9 — Постановка задачи

```
y = ⊕_{i=0}^{N−1} x_i = x_0 ⊕ x_1 ⊕ … ⊕ x_{N−1}
```

- Свёртка массива в **одно скалярное значение**.
- Операторы ⊕: сложение (Σ), умножение (Π), `min`, `max`, побитовые AND/OR/XOR.
- **Требования к оператору:**
  - **Ассоциативность:** `(a ⊕ b) ⊕ c = a ⊕ (b ⊕ c)` — критично, чтобы **перегруппировать** вычисления в произвольное дерево;
  - **Коммутативность:** `a ⊕ b = b ⊕ a` — свобода распределения данных между потоками (в каком порядке потоки «подхватят» элементы).
- **Сложность:** последовательно — время O(N), работа O(N); параллельное дерево — **глубина O(log₂ N), работа O(N)** (work-efficient).

> ⚠ **Ловушка:** для чисел с плавающей запятой **сложение НЕ ассоциативно** (из-за округлений). Изменение порядка суммирования меняет результат в последних разрядах → результаты CPU и GPU, а также разных запусков (с atomicAdd) **могут не совпадать побитово**. Это и есть «недетерминизм» из слайда 16. Для строгой воспроизводимости — фиксированное дерево (two-pass) или компенсированное суммирование (Kahan), либо суммирование в double.
> ➕ Для некоммутативных, но ассоциативных операторов (напр., конкатенация строк, умножение матриц) редукцию можно делать, но нужно **сохранять порядок операндов** (CUB поддерживает такой режим).
> ➕ Нейтральный элемент (identity): 0 для `+`, 1 для `×`, `+∞` для `min`, `−∞` для `max`, `0xFF…` для AND. Используется для **дополнения** неполных блоков.

🧮 **Пример дерева** для N = 8, ⊕ = +: уровень 1: (x0+x1),(x2+x3),(x4+x5),(x6+x7); уровень 2: две суммы; уровень 3: итог. **log₂8 = 3 шага**, всего 7 сложений = N − 1.

## 2.2. Слайд 10 — Иерархическая декомпозиция редукции в CUDA

- Массив из миллионов элементов не помещается в один SM.
- **Три уровня:**
  1. **Grid:** массив делится на независимые чанки между блоками;
  2. **Block:** потоки блока грузят данные в **Shared Memory** и делают локальную редукцию;
  3. **Warp:** внутри 32 потоков редукция выполняется **на регистрах** (shuffle).
- **Серия оптимизаций Марка Харриса (NVIDIA)** — классика:
  - **V1:** наивное дерево → проблема **дивергенции варпов**;
  - **V2:** чередующиеся индексы → проблема **bank conflicts**;
  - **V3:** последовательная адресация → идеальный шаблон доступа к Shared Memory.

> ➕ **Оригинальная серия Харриса** («Optimizing Parallel Reduction in CUDA») содержит **7 ядер**: K1 interleaved addressing с divergent branching; K2 interleaved addressing с bank conflicts (strided index); K3 sequential addressing; K4 **first add during global load** (каждый поток при загрузке складывает 2 элемента); K5 **unroll the last warp**; K6 **complete unroll** (шаблоны); K7 **multiple elements per thread** (algorithm cascading). Ускорение K7 над K1 на G80 — порядка **30×** (≈ 8,05 мс → 0,27 мс на 4M элементов; значения приблизительные). Слайд сокращает до трёх версий + shuffle.
> ➕ Почему вообще идём в Shared Memory: данные между потоками блока нужно обмениваться; регистры потоков приватны (кроме shuffle внутри варпа).

## 2.3. Слайд 11 — Версия 1: наивное дерево и дивергенция

```cuda
sdata[tid] = g_in[i];
__syncthreads();
for (unsigned int s = 1; s < blockDim.x; s *= 2) {
    if (tid % (2 * s) == 0)
        sdata[tid] += sdata[tid + s];
    __syncthreads();
}
if (tid == 0) g_out[blockIdx.x] = sdata[0];
```

- Интерливинг: на шаге `s` складываются элементы на расстоянии `s`; активны потоки с `tid % (2s) == 0`.
- **Критический дефект — Warp Divergence:** условие зависит от `tid` **внутри варпа**.
  - `s = 1`: активны чётные потоки (0, 2, 4, …) — половина варпа простаивает;
  - `s = 2`: активны 0, 4, 8, … — 75 % варпа простаивает;
  - …`s = 16`: активен 1 поток из 32 — **≈ 97 %** простоя (откуда «до 97 %» в таблице слайда 17).
- SM сериализует ветви: активные потоки исполняют инструкции, остальные маскируются.

➕ **Нюансы:**
- Оператор `%` (деление/остаток) **дорог** на GPU (десятки тактов) — ещё один минус V1 (заменяется на `tid & (2*s-1)`).
- **Дивергенция внутри варпа есть только при `s < 32`;** при `s ≥ 32` варп целиком либо активен, либо нет — дивергенции нет (но активные варпы всё равно «разрежены» по блоку).
- Синхронизация `__syncthreads()` после каждого шага обязательна: читаются данные, записанные другими потоками на предыдущем шаге.
- 🧮 Для блока 8 элементов `[1,2,3,4,5,6,7,8]`: s=1 → `[3,2,7,4,11,6,15,8]`; s=2 → `[10,2,7,4,26,6,15,8]`; s=4 → `[36,…]`. Итог `sdata[0] = 36` ✓.

## 2.4. Слайд 12 — Версия 2: устранение дивергенции (Strided Index)

```cuda
for (unsigned int s = 1; s < blockDim.x; s *= 2) {
    int index = 2 * s * tid;           // активные потоки сгруппированы в начале
    if (index < blockDim.x)
        sdata[index] += sdata[index + s];
    __syncthreads();
}
```

- Теперь активны **первые `blockDim/(2s)` потоков подряд** (tid = 0,1,2,…) → целые варпы активны/неактивны, **дивергенция устранена** (кроме последних шагов, когда активных потоков < 32).
- **Новая скрытая проблема — Bank Conflicts в Shared Memory:**
  - Shared Memory: **32 банка шириной 4 байта**; слово с индексом `w` лежит в банке `w mod 32`;
  - поток `tid` обращается к `sdata[2·s·tid]` → шаг между соседними потоками = `2s` слов;
  - `s = 1`: шаг 2 → 2-way конфликт; `s = 2`: шаг 4 → 4-way; `s = 4` → 8-way; … конфликты растут вдвое с каждым шагом (в таблице слайда 17: «до 16-way»).
- Итог: часть выигрыша от устранения дивергенции съедается сериализацией доступа.

🧮 **Пример конфликта:** шаг 2 слова → потоки 0 и 16 обращаются к словам 0 и 32 → оба в банк 0 → 2-way конфликт (потоки 0 и 16, 1 и 17 и т.д.).

## 2.5. Слайд 13 — Версия 3: последовательная адресация (Sequential Addressing)

```cuda
for (unsigned int s = blockDim.x / 2; s > 0; s >>= 1) {
    if (tid < s)
        sdata[tid] += sdata[tid + s];
    __syncthreads();
}
```

- Цикл «разворачивается»: начинаем с **половины блока** и уменьшаем шаг вдвое: `s = blockDim/2, /4, …, 1`.
- Активны потоки `tid < s` — **подряд с начала**: нет дивергенции (для целых варпов) и **нет конфликтов банков** — соседние потоки обращаются к соседним словам (`sdata[tid]`, `sdata[tid+s]`: оба «линейные»).
- Это **идеальный паттерн доступа к Shared Memory**.

➕ **Что остаётся неэффективным:** на первом шаге **половина потоков блока простаивает** (только `tid < blockDim/2` работают). Лечение у Харриса: **K4 — при загрузке из глобальной памяти каждый поток сразу складывает два элемента** (`sdata[tid] = g_in[i] + g_in[i + blockDim.x]`) → блок обрабатывает вдвое больше данных. Далее — разворачивание последнего варпа (`s < 32` не требует `__syncthreads()` в варп-синхронном исполнении) и полное разворачивание цикла шаблонами C++.
➕ Нет границ: слайды предполагают, что N кратно размеру блока; в общем случае нужно `sdata[tid] = (i < n) ? g_in[i] : 0` (нейтральный элемент).

## 2.6. Слайд 14 — Warp Shuffle: отказ от Shared Memory внутри варпа

```cuda
__device__ inline float warp_reduce_sum(float val) {
    unsigned int mask = 0xffffffff;          // все 32 потока варпа активны
    for (int offset = 16; offset > 0; offset /= 2)
        val += __shfl_down_sync(mask, val, offset);
    return val;       // результат — в потоке с laneId == 0
}
```

- **`__shfl_down_sync(mask, var, delta)`** — поток с номером `lane` получает значение `var` потока `lane + delta` (внутри варпа).
- Цикл: `offset = 16, 8, 4, 2, 1` — **5 шагов** (log₂32); после них в **lane 0** — сумма всех 32 значений.
- **Преимущества:** обмен идёт **через регистровый файл** (быстро, порядка нескольких тактов; в слайде «1–2 такта»), нет доступа в Shared Memory, нет `__syncthreads()`.
- **Предупреждение слайда:** старая функция **`__shfl_down`** (без `_sync`) на GPU, начиная с **Volta**, приведёт к ошибке.

🧮 **Трассировка** для 8 потоков (offset 4,2,1), значения `[1,2,3,4,5,6,7,8]`:
offset 4 → `[6,8,10,12,5,6,7,8]` (первые 4 = x[i]+x[i+4]); offset 2 → `[16,20,10,12,…]`; offset 1 → `[36,…]` в lane 0 ✓.

➕ **Нюансы:**
- Параметр **`mask`** — набор потоков, которые **обязаны** участвовать в вызове (и все выполнить одну и ту же инструкцию). `0xffffffff` корректно, только если **все 32 потока действительно сходятся** в этом месте кода (иначе неопределённое поведение).
- Причина появления `_sync`-версий — **Independent Thread Scheduling** (Volta, CC 7.0): потоки варпа **больше не гарантированно выполняются в lock-step**, поэтому неявная синхронность «внутри варпа» исчезла; нужна явная маска (и при необходимости `__syncwarp()`).
- Значения в потоках с `lane > 0` после цикла — **частичные суммы** (мусор для пользователя). Если нужен результат **во всех потоках**, используют **`__shfl_xor_sync`** (butterfly) или `__shfl_sync(mask, val, 0)` для широковещания.
- Если `lane + delta ≥ 32`, `__shfl_down_sync` возвращает **собственное** значение `var` потока (out-of-range) — поэтому в редукции «лишние» сложения допустимы, лишь бы значимый результат был в lane 0.
- Аналоги: `__shfl_up_sync` (для scan), `__shfl_xor_sync` (butterfly), `__shfl_sync` (произвольный источник). В CUDA 9+ есть также `__reduce_add_sync` (аппаратная редукция целых для CC 8.0+) и Cooperative Groups `cg::reduce`.

## 2.7. Слайд 15 — Полное решение: блок на warp-примитивах

```cuda
__global__ void reduce_warp_level(const float *g_in, float *g_out, int n) {
    __shared__ float warp_sums[32];                    // промежуточные суммы варпов
    int lane = threadIdx.x % 32, warp_id = threadIdx.x / 32;
    float val = g_in[blockIdx.x * blockDim.x + threadIdx.x];
    val = warp_reduce_sum(val);                        // 1) редукция внутри каждого варпа
    if (lane == 0) warp_sums[warp_id] = val;           // 2) лидер варпа пишет сумму в SMEM
    __syncthreads();
    if (warp_id == 0) {                                // 3) первый варп редуцирует суммы варпов
        float b_val = (lane < blockDim.x / 32) ? warp_sums[lane] : 0.0f;
        b_val = warp_reduce_sum(b_val);
        if (lane == 0) g_out[blockIdx.x] = b_val;      // сумма целого блока
    }
}
```

**Схема:** значения → warp-редукция (регистры) → 32 (макс.) частичных сумм в Shared Memory → один `__syncthreads()` → **первый варп** снова делает warp-редукцию → результат блока.

- Блок максимум **1024 потока = 32 варпа** → ровно 32 частичные суммы → **хватает одного варпа** для финальной редукции; поэтому `warp_sums[32]`.
- Только **один барьер** и **маленький** объём Shared Memory (128 байт) — высокий occupancy.

> ⚠ **Ловушка (код слайда):** параметр `n` не используется — **нет проверки границ** (`g_in[...]` читается без `if`); N должно быть кратно размеру блока. Размер блока должен быть **кратен 32** и ≤ 1024. Для неполных блоков заполнять нейтральным элементом (0).
> ➕ Для `blockDim.x = 256`: 8 варпов → в финальной стадии `lane < 8` читают значения, остальные 24 lane берут 0.0f (нейтральный элемент) — потому что **все 32 потока варпа должны выполнить shuffle**.

## 2.8. Слайд 16 — Межблочная редукция: атомики vs двухпроходный подход

**Проблема:** блоки на GPU **независимы** (нет глобального барьера внутри ядра). Как агрегировать частичные суммы блоков в один скаляр?

| Стратегия | Суть | Плюсы | Минусы |
|-----------|------|-------|--------|
| **А. Атомики** | `if (threadIdx.x == 0) atomicAdd(global_result, block_sum);` | один запуск ядра; не нужна дополнительная память | при тысячах блоков запросы к **одной ячейке** L2/DRAM **сериализуются**; **порядок суммирования недетерминирован** (критично для float) |
| **Б. Two-Pass** | Ядро 1: K блоков → массив `g_intermediate[0..K-1]`; Ядро 2: **1 блок** редуцирует этот массив | **полный детерминизм** порядка сложения; масштабируется на N > 10⁸ | накладные расходы на глобальный буфер и второй запуск ядра |

➕ **Нюансы:**
- `global_result` нужно **обнулить** до запуска (`cudaMemset`).
- `atomicAdd` для `float` доступен с CC 2.0 (глобальная), для `double` — с CC 6.0; для `int` — всегда.
- Атомик **один на блок** (не на поток!) — при ~10³–10⁴ блоков это немного; проблемы начинаются, когда атомик на каждый поток (как в гистограммах).
- **Третий вариант: single-pass с `__threadfence()` + атомарный счётчик «последний блок»** (CUDA sample `threadFenceReduction`): каждый блок пишет частичную сумму, делает `__threadfence()`, инкрементирует атомарный счётчик; **блок, увидевший счётчик == gridDim−1**, делает финальную редукцию. Один запуск + детерминизм порядка финальной свёртки (при фиксированном порядке чтения).
- **Cooperative Groups `grid.sync()`** — глобальный барьер, но требует **cooperative launch** (все блоки должны быть резидентны одновременно) → ограничение на размер сетки.
- Альтернатива для больших N: **grid-stride + малая сетка** → каждый поток накапливает много элементов, блоков мало → атомиков мало.

## 2.9. Слайд 17 — Сводная таблица эволюции Reduce

| Версия | Механизм передачи данных | Дивергенция варпов | Конфликты банков | Относительная скорость |
|--------|--------------------------|--------------------|------------------|------------------------|
| V1 Наивное дерево | Shared Memory (`% 2*s`) | Критическая (до 97 %) | Нет | 1,0× (база) |
| V2 С чередованием | Shared Memory (`2*s*tid`) | Устранена | Высокие (до 16-way) | ~1,5× |
| V3 Последовательная | Shared Memory (`tid < s`) | Устранена | Отсутствуют | ~2,5× |
| V4 Warp Shuffle + SM | Регистры варпа → SM | Отсутствуют | Отсутствуют | ~4,5–7× |

**Золотые правила (слайд 17):**
1. **Никакой Shared Memory внутри варпа:** `__shfl_down_sync`.
2. **Максимизируйте нагрузку на поток:** Grid-Stride Loop — один поток агрегирует **несколько элементов** (в регистре) перед запуском дерева.
3. **Минимизируйте глобальную синхронизацию:** `atomicAdd` для финальной сборки результата блока.

> ⚠ **Ловушка:** числа ускорения в таблице — **ориентировочные**, зависят от GPU и размера. Не заучивать как «законы». Правило 3 не противоречит слайду 16: речь про **один атомик на блок**, а не на поток.

# ЧАСТЬ 3. Паттерн SCAN / PREFIX SUM (слайды 18–28)

## 3.1. Слайд 18 — Определение

Дано: упорядоченная последовательность `[x0, x1, …, x_{n−1}]`, ассоциативный оператор ⊕, нейтральный элемент I.

| Вид | Формула | Пример (⊕ = +): вход `[3,1,7,0,4]` |
|-----|---------|-------------------------------------|
| **Inclusive scan** (включающий) | `y_i = x_0 ⊕ x_1 ⊕ … ⊕ x_i` | `[3, 4, 11, 11, 15]` |
| **Exclusive scan** (исключающий) | `y_0 = I`, `y_i = x_0 ⊕ … ⊕ x_{i−1}` | `[0, 3, 4, 11, 11]` |

- **Связь:** exclusive = inclusive, **сдвинутый вправо на 1** позицию, с подстановкой I в начало.
- Последний элемент **inclusive** скана = сумма всего массива (15). Сумма всего массива = `exclusive[n−1] + x[n−1]`.
- Перевод inclusive → exclusive: сдвиг; exclusive → inclusive: прибавить исходный элемент (`y_incl[i] = y_excl[i] + x[i]`) или сдвинуть влево с добавлением итога.

## 3.2. Слайд 19 — Зачем нужен Scan

- **Парадокс:** `y_i = y_{i−1} ⊕ x_i` — на вид строго последовательно (цепочка зависимостей длины N), но существует алгоритм с **полилогарифмической** глубиной.
- Применения:
  - **Stream Compaction** — фильтрация без «дыр» (слайд 27);
  - **Radix Sort** — вычисление целевых адресов элементов по разрядам;
  - **Динамическое выделение ресурсов** — смещения в общем буфере для переменного числа элементов от каждого потока **без атомарных счётчиков** (и с сохранением порядка);
  - **Разреженные матрицы (CSR)** — массив `row_ptr` = exclusive scan числа ненулевых по строкам;
  - **Деревья и сетки** (BVH, Octree) — параллельное определение индексов узлов.
- ➕ Также: сортировка слиянием (merge path), поиск границ сегментов, **segmented scan**, вычисление «первой/последней» позиции, интегральные изображения (summed-area table = scan по строкам и столбцам), решение рекуррентных соотношений (линейные рекуррентности через scan с оператором композиции).

## 3.3. Слайд 20 — Алгоритм Хиллса–Стила (Hillis–Steele)

- **1986 г.**, для SIMD-машин (**Connection Machine**). Вычисляет **inclusive** scan за `⌈log₂ N⌉` шагов; расстояние (stride) растёт как степень двойки.
- Шаг: для `d = 0, 1, …, ⌈log₂N⌉−1` с расстоянием `2^d`:

```
x^(d+1)[k] = x^(d)[k] + x^(d)[k − 2^d]   если k ≥ 2^d
x^(d+1)[k] = x^(d)[k]                    если k < 2^d
```

- **Span = O(log N)**.
- **Work** = Σ_{d=0}^{log₂N −1} (N − 2^d) = **N·log₂N − N + 1 = O(N log N)**.
- **Проблема:** **не work-efficient** (последовательный scan = O(N)); лишняя энергия/вычисления на больших массивах.
- Рисунок слайда: массив из 8 элементов `x0..x7`, три слоя (`d=1,2,3` на рисунке, т.е. расстояния 1, 2, 4), стрелки от `k−2^d` к `k`; в каждой ячейке записана частичная сумма `Σ(x_a..x_b)`.

🧮 **Пример** `[3,1,7,0,4,1,6,3]`:
- расстояние 1 → `[3,4,8,7,4,5,7,9]`
- расстояние 2 → `[3,4,11,11,12,12,11,14]`
- расстояние 4 → `[3,4,11,11,15,16,22,25]` ✓ (inclusive scan). Всего 3 = log₂8 шага; число сложений: 7 + 6 + 4 = 17 = 8·3 − 8 + 1 ✓.

➕ **Нюансы:**
- На каждом шаге **все потоки читают значения предыдущего шага**, а пишут новые → при работе «на месте» в Shared Memory возникает **гонка чтение/запись**: нужен **двойной буфер (ping-pong)** либо барьер между чтением и записью (потоки сначала читают в регистр, `__syncthreads()`, потом пишут).
- Рисунок на слайде нумерует слои `d = 1, 2, 3` (расстояния 1, 2, 4), а формула — `d = 0, 1, …` (расстояние `2^d`) — это одно и то же, просто смещение индексации.
- Предполагается N = степень двойки (иначе добивают нейтральным элементом).

## 3.4. Слайд 21 — Хиллс–Стил на GPU на уровне варпа

- Для малых N (например, N = 32 в одном варпе) накладные расходы сложной синхронизации превышают потери от избыточных операций; потоки варпа работают в режиме **SIMT** синхронно.
- Реализация через **`__shfl_up_sync`**: обмен через регистры, без Shared Memory и `__syncthreads()` (достаточно маски варпа). Сканирование 32 элементов = **ровно 5 шагов** (смещения 1, 2, 4, 8, 16):

```cuda
int val = threadIdx.x;   // пример входного значения
for (int offset = 1; offset < 32; offset *= 2) {
    int n = __shfl_up_sync(0xffffffff, val, offset);
    if (threadIdx.x >= offset) val += n;
}
// val — результат Inclusive Scan
```

- **Warp Scan — базовый «кирпичик»** для блочных и глобальных алгоритмов.

> ⚠ **Ловушка (код слайда):** условие `threadIdx.x >= offset` корректно **только если блок состоит ровно из одного варпа (32 потока)**. Для блока из нескольких варпов нужно использовать **номер lane**: `int lane = threadIdx.x & 31; if (lane >= offset) val += n;`.
> ⚠ Если `lane < offset`, `__shfl_up_sync` возвращает **собственное** значение потока, поэтому без условия `if (lane >= offset)` оно было бы добавлено само к себе (ошибка).
> ➕ `__shfl_up_sync(mask, var, delta)`: поток `lane` получает значение от `lane − delta`. Это зеркало `__shfl_down_sync`.
> ➕ Для **блока из W варпов** типичная схема: warp-scan в каждом варпе → последний lane каждого варпа записывает сумму варпа в Shared → один варп сканирует массив сумм → результат прибавляется к элементам соответствующих варпов.
> ➕ «Режим SIMT синхронно» — упрощение (см. Independent Thread Scheduling у Volta+): `__syncwarp()`/`_sync`-маски нужны.

## 3.5. Слайд 22 — Алгоритм Блеллока (Blelloch): work-efficient

- **Guy Blelloch, 1990.** Цель: параллельный scan с **O(N)** работой, как у последовательного.
- Изначально строит **exclusive** scan.
- Модель — **идеальное бинарное дерево**, листья = элементы массива. **Два прохода:**
  1. **Up-Sweep (снизу вверх)** — параллельная редукция, строит суммы поддеревьев;
  2. **Обнуление корня** (`A[N−1] = I = 0`);
  3. **Down-Sweep (сверху вниз)** — обратное распределение, формирование префиксов.
- **Сложность:** Work = O(N) (≈ 2(N−1) сложений; «до 2N» на слайде); Span = **O(log N)** (глубина ≈ 2·log₂N).

## 3.6. Слайд 23 — Up-Sweep

```
для d = 0 … log₂N − 1, для k = 0, 2^(d+1), 2·2^(d+1), … (параллельно):
    A[k + 2^(d+1) − 1] = A[k + 2^d − 1] + A[k + 2^(d+1) − 1]
```

- На вершине `A[N−1]` — сумма всех элементов.
- Затем **обнуление вершины:** `A[N−1] = 0`.
- Рисунок: три слоя (`d=0,1,2`), снизу вверх, стрелки от левого потомка к правому (в ячейке правого записывается сумма поддерева).

## 3.7. Слайд 24 — Down-Sweep

```
для d = log₂N − 1 … 0, для k = 0, 2^(d+1), … (параллельно):
    t = A[k + 2^d − 1]                         // сохраняем старое значение левого потомка
    A[k + 2^d − 1]     = A[k + 2^(d+1) − 1]    // левый получает значение родителя
    A[k + 2^(d+1) − 1] = t + A[k + 2^(d+1) − 1]// правый = старое левое + родитель
```

🧮 **Полный пример** `[3,1,7,0,4,1,6,3]` (N = 8):
- **Up-sweep:**
  - d=0: `[3,4,7,7,4,5,6,9]`
  - d=1: `[3,4,7,11,4,5,6,14]`
  - d=2: `[3,4,7,11,4,5,6,25]` (A[7] = 25 = сумма всех)
- **Обнуление корня:** `[3,4,7,11,4,5,6,0]`
- **Down-sweep:**
  - d=2: `t=A[3]=11; A[3]=A[7]=0; A[7]=11+0=11` → `[3,4,7,0,4,5,6,11]`
  - d=1: пары (1,3) и (5,7): `A[1]=0, A[3]=4+0=4; A[5]=11, A[7]=5+11=16` → `[3,0,7,4,4,11,6,16]`
  - d=0: пары (0,1),(2,3),(4,5),(6,7): `[0,3,4,11,11,15,16,22]`
- **Результат (exclusive scan)** `[0,3,4,11,11,15,16,22]` ✓. Inclusive = exclusive + вход: `[3,4,11,11,15,16,22,25]`.

➕ **Нюансы Блеллока на GPU:**
- Один блок из `B` потоков обрабатывает **`2B` элементов** (каждый поток — две ячейки).
- Требует **степени двойки** (иначе добивка нейтральным элементом).
- В Shared Memory доступ с шагом `2^(d+1)` порождает **bank conflicts** — классическое решение (GPU Gems 3, глава 39): **padding / сдвиг индекса** `idx + (idx >> 5)` (conflict-free offset).
- На каждом уровне `__syncthreads()`; активных потоков становится всё меньше (на верхних уровнях большинство простаивает) — отсюда практическая неэффективность по сравнению с warp-shuffle для малых N.
- Блеллок: **work-efficient**, но span вдвое больше, чем у Хиллса–Стила; для N ≈ 32–1024 в блоке практичнее комбинация «warp-scan (Hillis–Steele) + scan сумм варпов».

## 3.8. Слайд 25 — Масштабирование на GPU: Block-Scan-Add (3 прохода)

**Проблема:** массив — миллионы элементов; **глобального барьера между блоками нет** (`__syncthreads()` — только внутри блока).

1. **Pass 1 (Local Scan & Aggregate):** массив разбит на тайлы размером с блок; каждый блок в Shared Memory считает **локальный scan**; **последний элемент (сумма тайла)** пишется в массив сумм блоков `S`.
2. **Pass 2 (Scan of Block Sums):** `S` сканируется отдельным ядром (обычно в **одном блоке**, если N ≤ BlockSize²).
3. **Pass 3 (Uniform Add):** `S[b]` (scan) **прибавляется ко всем элементам тайла `b`** в глобальной памяти.

- **Недостаток:** высокий трафик памяти — **3× чтения и записи в VRAM**, **3 запуска ядра**.
- Ограничение «N ≤ BlockSize²»: если число блоков > размера блока, массив `S` не сканируется одним блоком → нужна **рекурсия** (ещё уровень).

➕ Варианты: **reduce-then-scan** (сначала только суммы тайлов, затем scan с учётом префикса — меньше записей), **scan-then-propagate** (как на слайде).

## 3.9. Слайд 26 — Single-pass Scan: Decoupled Look-back (Duane Merrill)

- **Duane Merrill (NVIDIA Research)**, основа **CUB** и **Thrust**: scan произвольного размера **за один проход одного ядра** с минимумом обращений к глобальной памяти (читает вход один раз, пишет выход один раз).
- **Принцип:**
  - блоки берут тайлы **динамически через атомарный счётчик** (`atomicAdd`) — нумерация тайлов по порядку взятия;
  - каждый блок считает **агрегат (сумму) своего тайла** и публикует статус в глобальном массиве дескрипторов:
    - **A (Aggregate available)** — сумма тайла посчитана;
    - **P (Prefix available)** — **полный префикс** (включая этот тайл) посчитан;
  - **Look-back:** чтобы получить своё базовое смещение, блок «оглядывается назад» по статусам предыдущих тайлов:
    - если у тайла слева статус **P** — читаем готовый префикс, прибавляем и **останавливаемся**;
    - если **A** — накапливаем агрегат и идём ещё левее.
- Достигает теоретического предела (**speed-of-light** по памяти ≈ скорости копирования).

> ⚠ **Ловушка:** в слайде перечислены два статуса, но у алгоритма их **три**: ещё **X (Invalid / not ready)** — тайл ещё ничего не опубликовал; блок **ждёт (spin)** на таком тайле. Статус и значение публикуются **атомарно вместе** (упакованы в одно слово) и с барьером памяти (`__threadfence`/acquire-release).
> ➕ **Почему атомарный счётчик для нумерации тайлов?** Без него порядок запуска блоков не гарантирован → блок мог бы ждать тайл, который ещё не запущен (из-за ограниченного числа резидентных блоков) → **взаимоблокировка**. С динамической нумерацией **предшественники всегда взяты раньше** → прогресс гарантирован.
> ➕ **Decoupled** = развязанный: агрегаты (A) публикуются независимо и не ждут префикса предшественников (в отличие от «chained scan» Yan et al. 2013, где каждый блок ждал полный префикс предыдущего → цепочка последовательных задержек). Look-back по A позволяет считать префикс «с запасом» и сокращает цепочку.
> ➕ Опубликована как технический отчёт NVIDIA (Merrill & Garland, 2016).

## 3.10. Слайд 27 — Stream Compaction (фильтрация потока)

- **Задача:** выбрать из массива элементы, удовлетворяющие предикату `P(x)`, **сохранив порядок**, и упаковать их **плотно** (без «дыр»).
- Почему не работает обычный цикл: `push_back()` в параллельной среде требует **атомарных блокировок**, разрушающих параллелизм (и не сохраняет порядок).
- **Три шага:**
  1. **Compute Predicate:** `b_i = P(x_i) ? 1 : 0` (Map);
  2. **Exclusive Scan:** `idx = ExclusiveScan(b)` — **`idx_i` — уникальный адрес записи** элемента `x_i`;
  3. **Scatter:** `if (b_i) output[idx_i] = x_i`.
- **Итоговый размер:** `idx_{N−1} + b_{N−1}`.

🧮 **Пример:** `x = [5,2,8,1,9,3]`, предикат `x > 3`:
- `b = [1,0,1,0,1,0]`
- `idx = exclusive scan(b) = [0,1,1,2,2,3]`
- запись: `x0=5 → out[0]`, `x2=8 → out[1]`, `x4=9 → out[2]` → `out = [5,8,9]`
- размер = `idx[5] + b[5] = 3 + 0 = 3` ✓.

➕ **Нюансы:**
- **Порядок сохраняется** (stable) именно благодаря scan; атомарный счётчик дал бы произвольный порядок.
- Паттерн = **Map + Scan + Scatter**; в библиотеках: `thrust::copy_if`, `cub::DeviceSelect::If/Flagged`.
- Варианты: **warp-level compaction** через `__ballot_sync` + `__popc` (считаем, сколько потоков варпа с меньшим lane выбрали элемент — это scan внутри варпа на 32 битах без shuffle).
- Применения: удаление «мёртвых» частиц/лучей, построение списков кандидатов, подготовка CSR.

## 3.11. Слайд 28 — Сравнение подходов к сканированию

| Алгоритм | Work | Span | Применение |
|----------|------|------|------------|
| Последовательный (CPU) | O(N) | O(N) | один поток CPU |
| Hillis–Steele | O(N log N) | O(log N) | уровень **Warp** (32), регистры `__shfl` |
| Blelloch | O(N) | O(log N) | уровень **Thread Block**, Shared Memory |
| Block-Scan-Add | O(N) | O(log N) | устаревший мультиблочный подход (3 прохода) |
| Decoupled Look-back | O(N) | O(log N) | современный глобальный GPU Scan (**CUB**) |

> ➕ Общая схема современного scan: **Hillis–Steele на уровне варпа** → scan сумм варпов в блоке → **Decoupled Look-back между блоками**.

# ЧАСТЬ 4. Паттерн STENCIL (слайды 29–37)

## 4.1. Слайд 29 — Суть и математическая модель

- **Stencil (трафарет):** значение каждого элемента сетки на шаге `t+1` — функция значений **этого же элемента и фиксированного набора соседей** на шаге `t`.
- **2D-формула:**

```
u^{t+1}_{i,j} = c₀ · u^t_{i,j} + Σ_{(k,l)∈𝒩} c_{k,l} · u^t_{i+k, j+l}
```

где 𝒩 — окрестность (трафарет), `c` — весовые коэффициенты (константные или переменные).
- Примеры трафаретов: **5-точечный** (крест: центр + 4 соседа, радиус R = 1; метод конечных разностей, Лаплас), **9-точечный** (3×3 «квадрат»), **7-точечный** в 3D.
- **Сферы применения:** численные методы ДУЧП (теплопроводность, волны, гидродинамика); обработка изображений (фильтры Гаусса, Собеля, Лапласа, медианный, размытие); **свёртка (Convolution)** в глубоком обучении.
- **Главная проблема GPU:** высокое **перекрытие обращений по памяти** (соседние точки читают одни и те же данные) при **малом числе операций на байт** → **memory-bound**.

➕ **Нюансы:**
- Для итеративных схем (Jacobi) нужны **два массива** (`u_old`, `u_new`) с обменом ролей (**ping-pong**); обновление «на месте» вызвало бы гонку (поток читает соседа, который уже обновлён другим потоком).
- Без кэширования каждый выходной элемент 5-точечного трафарета читает **5 значений** из глобальной памяти, хотя «уникальных» данных ~1 на элемент → избыточность ×5 (реальная — меньше за счёт кэшей).
- **Stencil vs Convolution:** по структуре одно и то же, различие терминологическое (stencil — обычно «на сетке с коэффициентами схемы», convolution — «ядро свёртки»; в математике свёртка отражает ядро).

## 4.2. Слайд 30 — Тайлинг и Halo (Ghost Cells)

- Сетку разбивают на **тайлы**; блок потоков грузит тайл в **Shared Memory**, где данные переиспользуются всеми потоками блока.
- **Структура тайла:**
  - **Core region** — область `Tx × Ty`, новые значения которой считает этот блок;
  - **Halo / Ghost cells / Ореол** — кайма шириной **R** (радиус трафарета); данные **только читаются**, нужны для расчёта краёв ядра.
- **Размер Shared Memory:** `Smem = (Tx + 2R) × (Ty + 2R) × sizeof(Element)`.
  - 5-точечный: **R = 1**; блок 16×16 → тайл **18×18** элементов = 324 элемента.
- **Накладные расходы halo:** отношение площадей ≈ `2R(Tx+Ty)/(Tx·Ty)` — чем больше тайл, тем меньше доля halo, но больший тайл ограничен размером Shared Memory SM.

🧮 **Пример:** `Tx=Ty=16, R=1`: core 256, всего 324 → halo = 68 элементов = **≈ 26,6 %** (точная формула `(4R² + 2R(Tx+Ty))/(Tx·Ty) = 68/256`; приближение слайда даёт 25 %). Для 5-точечного «креста» **угловые** ячейки не нужны (4 из 68), для 9-точечного — нужны.
🧮 Для `Tx=Ty=32, R=1`: 34×34 = 1156; halo ≈ 12,9 %.

➕ **Выигрыш тайлинга:** каждый элемент core читается из глобальной памяти **один раз** (плюс halo), а используется 5 раз (из Shared). Чем больше R (3D-схемы высокого порядка), тем больше halo и тем дороже тайлинг.

## 4.3. Слайд 31 — Обработка краевых эффектов

**Два типа границ:**
1. **Внутренние (между тайлами):** ячейки halo физически есть в глобальной памяти (в соседних тайлах) — решается **корректной загрузкой соседних ячеек в Shared Memory до `__syncthreads()`**.
2. **Внешние (границы всей сетки):** точки за пределами массива — нужны **краевые условия (Boundary Conditions):**
   - **Дирихле:** за границей `u = const` (например, фиксированная температура стенки);
   - **Неймана (нулевой градиент / отражение):** значение берётся из ближайшей валидной граничной ячейки (**Clamp to edge**);
   - **Периодические (тор):** чтение с противоположного конца области: `x_periodic = (x + W) mod W`.
- После наполнения тайла в Shared Memory **обязателен `__syncthreads()`**, иначе вычисления начнутся на неполных данных.

> ⚠ **Ловушка:** **clamp-to-edge** — это «повтор последнего значения» (нулевая производная); **отражение (mirror)** — зеркальное (`−1 → 1`); эти режимы различаются. Условие Неймана в общем случае задаёт **производную** на границе, а не просто копию значения (копия — его простейшая аппроксимация).
> ⚠ Формула периодичности `(x + W) mod W` корректна для `x ≥ −W`; для произвольных смещений в C/C++ оператор `%` на **отрицательных числах** даёт отрицательный остаток → используют `((x % W) + W) % W`.
> ➕ Дирихле на практике — «подставить константу вместо чтения»; в тайле — условие `if (gx<0 || gx>=W) val = const`.

## 4.4. Слайд 32 — Загрузка Halo: расхождение ветвей

**Наивный подход «граничные потоки догружают Halo»:**
- Размер блока = размер core `Tx × Ty`; каждый поток читает 1 элемент в центр тайла;
- потоки на краях блока дополнительно грузят ореол по `if`:

```cuda
if (threadIdx.x == 0)              shm[y][0]            = global[...];
if (threadIdx.x == blockDim.x - 1) shm[y][blockDim.x+1] = global[...];
```

**Почему плохо:**
- **Warp Divergence:** в краевых варпах часть потоков читает, остальные простаивают;
- **Некоалесцированный доступ:** догрузка **вертикальных границ** (левый/правый столбцы halo) идёт с большим шагом (stride = width) → много неэффективных транзакций DRAM.

**Альтернатива «раздутый блок потоков»:** запуск `(Tx+2R) × (Ty+2R)` потоков, каждый грузит свой элемент (без ветвлений); **минус:** на этапе вычислений halo-потоки простаивают (`if (!is_halo) compute();`) → падает полезная загрузка SM; кроме того блок может превысить лимит 1024 потока (для 32×32 + halo = 34×34 = 1156 > 1024!).

> ➕ Верхний и нижний halo (строки) читаются коалесцированно, проблемные — именно **левый/правый столбцы** (по 1 элементу из разных строк).

## 4.5. Слайд 33 — Кооперативная загрузка (Cooperative Loading / Strided Loading)

- **Разделяем геометрию вычислений и геометрию загрузки:** тайл Shared Memory рассматривается как **одномерный массив** размера `N_shm = (Tx+2R)(Ty+2R)`.
- Потоки получают плоский id: `tid = threadIdx.y * blockDim.x + threadIdx.x`; цикл:

```cuda
for (int i = tid; i < N_shm; i += N_threads) {
    int gx = block_origin_x + (i % ShmWidth) - R;
    int gy = block_origin_y + (i / ShmWidth) - R;
    gx = min(max(gx, 0), Width  - 1);   // clamp на границах
    gy = min(max(gy, 0), Height - 1);
    shm[i] = global_in[gy * Width + gx];
}
__syncthreads();
```

- **Преимущества:** нет ветвлений внутри варпа, потоки загружают подряд идущие элементы.

🧮 Для блока 16×16 (256 потоков) и тайла 18×18 = 324: цикл делает **2 итерации** (256 + 68 элементов); во второй итерации работают только 68 потоков (часть варпов).

> ⚠ **Ловушка:** слайд говорит «полное коалесцирование» — строго говоря, ряды тайла длиной `Tx+2R = 18` слов (72 байта) **не кратны** размеру транзакции 32/128 байт → часть обращений **непрерывна внутри строки, но выровнена неидеально**; на практике почти оптимально, но не «идеально». Кроме того, деление и остаток `i / ShmWidth`, `i % ShmWidth` — **дорогие целочисленные операции** (оптимизируют сдвигами при ShmWidth — степень двойки или использованием 2D-индексации).
> ⚠ Пример кода реализует краевое условие **Clamp (Нейман)**; для Дирихле или периодики нужен другой код доступа.

## 4.6. Слайд 34 — Альтернатива 1: аппаратные L1/L2 кэши и `__ldg()`

- Современные архитектуры (Kepler/Pascal/Volta/Ampere/Hopper) имеют **кэши L1 и L2** с высокой пропускной способностью; существует **Read-Only Data Cache**.
- Квалификаторы **`const Element* __restrict__ in`** сообщают компилятору, что данные только читаются и **не имеют псевдонимов** → он генерирует **LDG** (load via read-only cache). `__ldg(&ptr[i])` — явная форма.
- **Stencil без ручного тайлинга:**

```cuda
float res = c0 * __ldg(&in[y*W + x]) +
            c1 * (__ldg(&in[(y-1)*W + x]) + __ldg(&in[(y+1)*W + x]) +
                  __ldg(&in[y*W + (x-1)]) + __ldg(&in[y*W + (x+1)]));
```

- **Плюс:** предельная простота кода (нет Shared Memory, нет `__syncthreads()`, нет маппинга halo).
- **Минус:** вертикальные обращения с большим шагом строки могут вызвать **конфликты строк в L1 (Cache Thrashing)**.

> ⚠ **Ловушка:** «специализированный кэш константных данных (Read-Only Data Cache)» — смешаны два разных понятия: **constant cache** (для `__constant__`-памяти, оптимизирован под broadcast) и **read-only/texture data cache** (для `LDG`). В Volta и новее L1 и texture-кэш **объединены** (unified L1/Tex), поэтому `__ldg` часто не даёт выигрыша относительно обычного `const __restrict__`.
> ⚠ Код слайда **не проверяет границы** (`y−1`, `x−1` на краях → выход за массив). И «пропускная способность сопоставима с Shared Memory» — упрощение: у Shared Memory **детерминированная задержка и полный контроль**, у кэша — попадания/промахи не гарантированы.

## 4.7. Слайд 35 — Альтернатива 2: текстурная память (Texture Objects)

- **Texture Unit (TMU)** — выделенный аппаратный блок под **2D/3D пространственную локальность**.
- **Преимущества:**
  - **2D-пространственное кэширование:** данные размещены не построчно (row-major), а по **кривой Z-порядка (Мортона / swizzled layout)** → промахи малы **и по X, и по Y**;
  - **Аппаратная обработка границ:** `cudaAddressModeClamp` (повтор граничных пикселей), `cudaAddressModeWrap` (зацикливание координат) — **без `if` и `min/max`** в ядре.
- **Недостатки:**
  - сложная подготовка: **CUDA Array**, `cudaResourceDesc`, `cudaTextureDesc`, `cudaCreateTextureObject`;
  - **только чтение** (результат пишется в обычный глобальный буфер);
  - ограничения по типам: лучше всего целые и `float` (для `double` — выигрыш меньше/нужны трюки).

> ➕ **Нюансы:**
> - Режимы адресации **Wrap и Mirror** работают **только с нормализованными координатами** (`normalizedCoords = 1`, координаты в [0,1)); Clamp и Border — с обоими типами.
> - **Аппаратная линейная интерполяция** (`cudaFilterModeLinear`) бесплатна, но работает для возвращаемых типов `float` (нормализованные целые → float); для целых «как есть» нужен point-фильтр.
> - Текстуру можно привязать не только к `cudaArray`, но и к **линейной/pitched памяти** (с ограничениями кэширования); legacy «texture references» удалены в CUDA 12 — используются **texture objects**.
> - Точная раскладка текстурной памяти **не документирована** (Z-order — модель, реально — оптимизированная проприетарная «block-linear»).

## 4.8. Слайд 36 — Кривая Z-порядка (Мортона)

- Рисунок: слева — рекурсивная «Z»-кривая (1 уровень: буква Z; 2 уровня: Z из Z; и т.д.), справа — таблица 8×8 с индексами (0…63), помеченными вдоль строк и столбцов смещениями.
- **Принцип:** индекс Мортона получается **чередованием (interleave) битов координат x и y**:

```
morton(x, y) = Σ_i ( x_i << 2i  |  y_i << (2i+1) )
```

🧮 **Пример:** `x = 5 (101₂)`, `y = 3 (011₂)` → биты x на позициях 0,2,4: `1,0,1` → 1 + 16 = **17**; биты y на позициях 1,3,5: `1,1,0` → 2 + 8 = **10**; индекс = 17 + 10 = **27** ✓ (в таблице слайда на пересечении строки «10» и столбца «17» стоит 27).
Смещения столбцов (x = 0…7): `0,1,4,5,16,17,20,21`; смещения строк (y = 0…7): `0,2,8,10,32,34,40,42` — именно это написано на осях таблицы.

- **Свойство:** близкие по (x,y) ячейки имеют **близкие индексы** → хорошая локальность в кэше при обращении к 2D-окрестностям.
- Применения: текстуры, **BVH/Octree** (Morton codes), Z-order в базах данных/ГИС.

## 4.9. Слайд 37 — Сравнение стратегий реализации Stencil

| Критерий | Shared Memory (Tiling) | Кэш L1 / `__ldg()` | Текстурная память |
|----------|------------------------|--------------------|-------------------|
| Сложность кода | **Высокая** (индексы, барьеры) | **Минимальная** (как CPU-код) | Средняя (много API-обвязки на хосте) |
| Обработка Halo | Ручная загрузка, явный учёт границ | Автоматически через аппаратный кэш | Аппаратно (контроллер TMU) |
| Контроль локальности | 100 % программный детерминизм | Аппаратный (возможны промахи) | Аппаратный с поддержкой 2D/3D-раскладки |
| Накладные расходы | Расход Shared Memory, задержки `__syncthreads()` | Нет расходов Shared Memory | Нет расходов Shared Memory |
| Поддержка double | Полная | Полная | Ограниченная аппаратная |

➕ **Выбор:** малый радиус, простая задача → **L1/`__ldg`** (меньше кода); большой радиус/3D/требуется предсказуемость → **Shared Memory tiling** (+ register tiling по оси z для 3D); сложные границы (clamp/wrap) и 2D-доступ → **текстуры**. Для 3D часто применяют **2.5D-блокирование**: тайл в плоскости XY в Shared, а по Z — «скользящее окно» в регистрах.

# ЧАСТЬ 5. SCATTER / GATHER и ГИСТОГРАММЫ (слайды 38–46)

## 5.1. Слайд 38 — Gather, Scatter, Histogram

- **Gather (сбор):** `y[i] = A[idx[i]]` — параллельное **чтение** по нерегулярным индексам; **конфликтов записи нет** (каждый поток пишет в свой `y[i]`).
- **Scatter (разброс):** `A[idx[i]] += y[i]` — параллельная **запись** по вычисляемым индексам; **гонки данных (Data Races)**, если `idx[i] == idx[j]` при `i ≠ j`.
- **Гистограмма — классический Scatter:**
  1. читаем `x_i`;
  2. определяем корзину (bin): `b = f(x_i)`;
  3. атомарный инкремент: `H[b] ← H[b] + 1`.
- **Ключевая проблема на GPU:** **зависимость производительности от распределения входных данных** (Data-dependent Performance).

➕ **Нюансы:**
- Gather: чтение нерегулярное → **некоалесцированное**, но безопасное. Если индексы соседних потоков близки (локальность) — быстро; если случайные — каждая транзакция 32 байта берёт лишь 4 полезных (эффективность ~12 %).
- Scatter без дубликатов (индексы — **перестановка**) безопасен. Scatter с дубликатами требует **атомиков** или **редукции по ключу** (sort + reduce_by_key).
- Gather/scatter в Stream Compaction (слайд 27): scatter безопасен, т.к. `idx` уникальны.
- Примеры: `y = A[idx]` (embedding lookup в нейросетях = gather), `index_add_` / `scatter_add` (backprop по embedding = scatter с накоплением).

## 5.2. Слайд 39 — Проблема конкуренции (Contention) и атомики

```cuda
__global__ void naiveHistogram(const int* data, int* hist, int N) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < N) {
        int bin = data[idx];
        atomicAdd(&hist[bin], 1);       // напрямую в Global Memory
    }
}
```

- `atomicAdd` обеспечивает атомарность **Read-Modify-Write (RMW)**.
- Если **K потоков** обращаются к **одной ячейке**, блок L2/контроллер памяти выстраивает их **в очередь (сериализация)**.
- **Деградация:**
  - в идеале при равномерном распределении по разным корзинам — O(1) параллельных шагов;
  - в худшем случае (все пишут в один bin) — время растёт до **O(N)** — как у одного последовательного потока.

> ⚠ Код слайда предполагает, что `data[idx]` **уже является номером корзины** в диапазоне `[0, numBins)`. В реальной задаче `bin = f(x)` вычисляют (`(x - min) / width`, с проверкой границ).

## 5.3. Слайд 40 — Аппаратная цена глобальных атомиков

- В современных GPU целочисленные атомики выполняются **в кэше L2** (в специальном блоке Atomic ALU). Путь: `SM → Interconnect/Crossbar → L2 Cache Partition → Atomic ALU`.
- **Узкие места при высокой конкуренции:**
  - переполнение буферов **MSHR** (Miss Status Holding Register) и очередей запросов контроллеров памяти;
  - «затопление» внутренней шины (**Crossbar switch**) повторными транзакциями (replay);
  - простой варпов (**Warp Stall**) — причины вида *Memory Throttle / Wait Memory*.
- **Падение пропускной способности:** пик Global Memory — сотни–тысячи ГБ/с; при 100 % коллизий — **на 2–3 порядка меньше**.

➕ **Нюансы:**
- Атомики на **разные** адреса идут параллельно (по числу L2-слайсов/банков); проблема — **один адрес**.
- Throughput атомиков на один адрес — порядка **одной операции за такт L2**, т.е. сотни миллионов–миллиарды/с; но по сравнению с обычным доступом это резко мало.
- Названия причин простоя в профайлере (ncu): `Stall Long Scoreboard` (ожидание глобальной памяти), `Stall LG Throttle` / `Memory Throttle` (очередь запросов переполнена).
- Атомики float в Global — с CC 2.0; **атомики в Shared Memory** — аппаратные с Maxwell (CC 5.0); на Kepler реализованы через **lock/update/unlock-циклы** и медленнее.

## 5.4. Слайд 41 — Паттерн Приватизации (Privatization)

- **Концепция:** заменить **единое разделяемое состояние** на **локальные копии (приватные буферы)**, накопить локально, потом слить.
- **Иерархия GPU:** Global Memory — медленная, единая на чип; **Shared Memory — быстрая, на блок**.
- **Две фазы:**
  1. **Локальное накопление:** каждый блок создаёт подгистограмму `H_shared` в Shared Memory, обрабатывает свою часть входа;
  2. **Глобальная редукция:** потоки блока сливают результат: `H_global[b] += H_shared[b]`.
- **Сокращение нагрузки на L2:** если блок обрабатывает M элементов (M ≫ B, B — число корзин), глобальных атомиков **не M, а B на блок**.

🧮 **Пример:** блок обрабатывает M = 100 000 элементов, B = 256 корзин → глобальных атомиков **256** вместо 100 000 (в ~390 раз меньше).

## 5.5. Слайд 42 — Ядро с приватизацией

```cuda
__global__ void privatizedHistogram(const int* data, int* hist, int N, int numBins) {
    extern __shared__ int s_hist[];                       // динамическая Shared Memory
    // 1. Инициализация нулями
    for (int i = threadIdx.x; i < numBins; i += blockDim.x) s_hist[i] = 0;
    __syncthreads();
    // 2. Локальное накопление (Grid-Stride Loop)
    int tid = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = blockDim.x * gridDim.x;
    for (int i = tid; i < N; i += stride) {
        int bin = data[i];
        atomicAdd(&s_hist[bin], 1);                       // атомик в Shared Memory!
    }
    __syncthreads();
    // 3. Слияние в Global Memory
    for (int i = threadIdx.x; i < numBins; i += blockDim.x)
        if (s_hist[i] > 0) atomicAdd(&hist[i], s_hist[i]);
}
```

**Что важно:**
- `extern __shared__` — **динамически выделяемая** Shared Memory; её размер задаётся третьим параметром запуска: `kernel<<<grid, block, numBins * sizeof(int)>>>(…)`.
- Три барьера/фазы: init → накопление → слияние. **Барьер после инициализации** обязателен (иначе поток может прибавить к ещё не обнулённой ячейке); **барьер после накопления** — перед чтением `s_hist`.
- **`if (s_hist[i] > 0)`** — пропуск нулевых корзин → меньше глобальных атомиков.
- Grid-Stride Loop здесь = каждый поток обрабатывает много элементов → блоков можно запускать мало (по числу SM), глобальных атомиков = `B × число_блоков`.
- Нет проверки `bin < numBins` (как в слайде 39).
- `hist` должен быть обнулён до запуска (`cudaMemset`).

## 5.6. Слайд 43 — Ограничения Shared Memory и bank conflicts

- Shared Memory — **32 банка шириной 4 байта**. Разные потоки варпа → **разные адреса одного банка** → **bank conflict** (сериализация).
- Если несколько потоков пишут через `atomicAdd` в **одну и ту же корзину** → **аппаратная сериализация атомиков внутри SM**.
- **Лимиты:** размер Shared Memory на SM **48 КБ – 228 КБ** (зависит от архитектуры); при B корзинах нужно **B × 4 байт на блок**; если корзин много (B = 256K для 18-битных чисел) — гистограмма **не помещается**.
- **Когда приватизации недостаточно:** сильный дисбаланс (все потоки варпа бьют в одну корзину Shared Memory) → внутриблочное бутылочное горлышко.

🧮 Ёмкость: 48 КБ / 4 Б = **12 288 корзин** (по умолчанию); при 227 КБ (Hopper, через `cudaFuncSetAttribute(…, cudaFuncAttributeMaxDynamicSharedMemorySize, …)`) ≈ 58 000. Для B = 256K: 256 K × 4 Б = **1 МБ** — не помещается.
➕ Нюанс: Shared Memory на блок > 48 КБ требует **явного включения** (opt-in) атрибутом функции. Большой объём Shared на блок уменьшает **occupancy** (меньше блоков на SM) — компромисс.
➕ Если корзин мало (например, 256) и данные неравномерны — **реплицируют** подгистограмму по варпам (`s_hist[warp][bin]`), чтобы разные варпы не конфликтовали; потом суммируют.

## 5.7. Слайд 44 — Warp Aggregation (внутриварповая агрегация)

- **Идея:** зачем 32 отдельных атомика, если потоки варпа «знают» данные друг друга?
- **Принцип:**
  - редукция **одинаковых значений прямо в регистрах варпа** через межпоточный обмен;
  - для каждого **уникального** значения в варпе выбирается **лидер**;
  - лидер выполняет **один** `atomicAdd` с весом `Δ = число потоков варпа с таким же bin`.
- **Эффект:** худший случай (все 32 пишут в один bin): 32 атомика → **1** (до **32×** меньше трафика). Накладные расходы — несколько регистровых инструкций (на порядок дешевле обращений в память).

## 5.8. Слайд 45 — Реализация через `__match_any_sync`

- **`unsigned int __match_any_sync(unsigned mask, T value)`** (начиная с **Volta**): сравнивает `value` текущего потока со значениями остальных активных потоков варпа и **возвращает битовую маску** потоков с тем же значением.

```cuda
__device__ void warpAggregateAdd(int* address, int bin) {
    unsigned int active     = __activemask();
    unsigned int match_mask = __match_any_sync(active, bin);   // маска потоков с таким же bin
    int count  = __popc(match_mask);                           // вес = число совпавших
    int leader = __ffs(match_mask) - 1;                        // лидер = младший установленный бит
    if ((threadIdx.x & 31) == leader) atomicAdd(address, count);
}
```

- `__popc(mask)` — **population count** (число единичных бит) = число потоков с этим bin.
- `__ffs(mask)` — индекс **первого установленного бита (1-based)**, поэтому `−1` → номер lane лидера.
- Только **лидер** обращается к памяти.

🧮 **Пример:** в варпе 32 потока, bin = 7 у потоков 2, 5, 9, 31. `match_mask` для этих потоков = `1<<2 | 1<<5 | 1<<9 | 1<<31`; `count = 4`; `leader = 2` → поток 2 выполняет `atomicAdd(&hist[7], 4)`. Остальные 3 потока ничего не делают.

> ⚠ **Ловушка (код слайда):** `__activemask()` в начале функции показывает, какие потоки **сейчас случайно сошлись** — при дивергенции может вернуть неполную маску → результат ненадёжен. Безопаснее передавать **явную маску** (известную из логики кода, например `0xffffffff` при полном варпе). `(threadIdx.x & 31)` корректно как **lane id** только для **1D-блока**.
> ➕ До Volta (`__match_any_sync` нет) агрегацию делали циклом по `__ballot_sync`/`__shfl_sync`. NVIDIA описывает паттерн в блоге «Voting and Shuffling to Optimize Atomic Operations» (**warp-aggregated atomics**); современный компилятор nvcc для **одинакового адреса** во всех потоках варпа делает такую агрегацию **автоматически**. Cooperative Groups: `cg::coalesced_threads()`.
> ➕ Метод эффективен, когда **много дубликатов bin внутри варпа**; на равномерных случайных данных с большим числом корзин дубликатов мало, и накладные расходы `match_any` могут не окупиться.

## 5.9. Слайд 46 — Выбор стратегии

| Стратегия | Скорость при коллизиях | Память | Ограничения по размеру |
|-----------|------------------------|--------|------------------------|
| **Наивная (Global Atomics)** | очень низкая (O(K)) | не требует Shared | любой размер гистограммы |
| **Приватизация (Shared Mem)** | высокая для **равномерных** данных | Shared на блок (B × 4 Б) | B ≤ лимита Shared |
| **Warp Aggregated Privatization** | максимум (устойчива к пикам) | Shared на блок | B ≤ лимита Shared |
| **Direct Warp Aggregation** | высокая (без Shared) | не требует Shared | любой размер |

**Практические рекомендации:**
1. Мало корзин (**B ≤ 1024**), нет экстремальных выбросов → **Privatization в Shared Memory**.
2. Мало корзин + сильный дисбаланс → **Warp Aggregated Privatization**.
3. Много корзин (**B ≫ 16K**), не влезает в Shared → **Direct Warp Aggregation** сразу в Global (убирает пики конкуренции в L2).
4. Экстремально разреженные/огромные гистограммы → **Sort and Reduce-by-key** (сортировка по ключу + редукция).

➕ В реальной жизни: **`cub::DeviceHistogram::HistogramEven/HistogramRange`** (выбирает стратегию сам), Thrust: сортировка + `reduce_by_key` / `upper_bound` для общей гистограммы.
➕ Для **детерминированного** целочисленного результата порядок атомиков не важен (целочисленное сложение ассоциативно и коммутативно), в отличие от float-гистограмм (взвешенных).

# ЧАСТЬ 6. MATRIX TILING / GEMM (слайды 47–55)

## 6.1. Слайд 47 — Задача GEMM и арифметическая интенсивность

- **GEMM (General Matrix Multiply):** `C = α·(A·B) + β·C`, `A ∈ ℝ^{M×K}`, `B ∈ ℝ^{K×N}`, `C ∈ ℝ^{M×N}` — базовый блок HPC и нейросетей.
- При `M = N = K`: **FLOPs = 2N³** (умножение + сложение на каждую из N³ итераций); размер данных `3N²·sizeof(float) = O(N²)`.
- **Подвох наивной реализации:** каждый поток считает один `C_{i,j} = Σ_k A_{i,k}·B_{k,j}` → читает строку A (N чисел) и столбец B (N чисел) из Global Memory. Суммарно читается **2N³ чисел float**.
- **Арифметическая (операционная) интенсивность:**

```
I = 2N³ FLOP / (2N³ × 4 байт) = 0,25 FLOP/байт
```

- **Вердикт:** алгоритм **глубоко в зоне Memory-Bound**; вычислительные блоки простаивают, ожидая DRAM.

➕ **Нюансы:**
- 0,25 FLOP/B — оценка «**без учёта кэшей**» (каждая операция тянет 2 float из DRAM). Реальный трафик меньше за счёт L1/L2, но всё равно далёк от оптимума.
- «**Ridge point**» roofline-модели: `I_ridge = Peak_FLOPS / Peak_BW`. Для A100 (FP32 ≈ 19,5 TFLOP/s, HBM2 ≈ 1,5 ТБ/с) ≈ **12–13 FLOP/B**. Чтобы GEMM стал compute-bound, интенсивность должна превысить ~13 → нужен тайлинг + register blocking.
- Идеальная («бесконечный кэш») интенсивность GEMM: `2N³ FLOP / (3N²·4 B) = N/6 FLOP/B` — растёт с N → GEMM **потенциально compute-bound**, если грамотно использовать иерархию памяти.
- Оценка чтения «столбца B»: в row-major столбец — это **шаг N** → некоалесцированно, если поток читает «свой» столбец; в наивном ядре с `col = threadIdx.x` соседние потоки читают соседние столбцы одной строки B (коалесцированно), но элементы A одной строки читаются всеми потоками одного варпа (broadcast).

## 6.2. Слайды 48–49 — Тайлинг на уровне блоков: Global → Shared

**Рисунок слайда 48:** матрицы `A (M×K)`, `B (K×N)`, `C (M×N)`. Блок `Block(m,n)` вычисляет плитку `C` размером `Mtile × Ntile` (зелёная); для неё в каждой итерации цикла по K загружается **полоска A** (`Mtile × Ktile`, синяя) и **полоска B** (`Ktile × Ntile`, жёлтая).

**Идея тайлинга:**
- разбиваем матрицы на квадратные плитки `B × B` (`TILE_DIM`);
- потоки блока **кооперируются**, загружая одну плитку A и одну плитку B из Global в Shared;
- **переиспользование:** каждый элемент загруженной плитки используется `B` потоками блока → **обращений к Global в B раз меньше**.

**Новая интенсивность** (за одну пару плиток): `I_shared ≈ 2B³ FLOP / (2B² · 4 Б) = B/4 FLOP/байт`.
- При **B = 32:** `32/4 = 8 FLOP/байт` — **в 32 раза** лучше наивных 0,25.

🧮 **Расчёт:** плитка 32×32: загружаем 2·1024 float = 8 КБ, делаем 2·32³ = 65 536 FLOP → 8 FLOP/B ✓.

➕ **Нюансы:**
- Суммарные чтения из Global: вместо `2N³` слов — `2N³/B` слов.
- Ограничение: размер плитки лимитируется Shared Memory (2 плитки 32×32 float = 8 КБ) и числом потоков (32×32 = 1024 = максимум на блок).

## 6.3. Слайд 50 — Реализация Tiled GEMM

```cuda
#define TILE_DIM 32
__global__ void gemm_shared_tiled(const float* A, const float* B, float* C, int N) {
    __shared__ float s_A[TILE_DIM][TILE_DIM], s_B[TILE_DIM][TILE_DIM];
    int row = blockIdx.y * TILE_DIM + threadIdx.y;
    int col = blockIdx.x * TILE_DIM + threadIdx.x;
    float sum = 0.0f;
    for (int k_tile = 0; k_tile < N / TILE_DIM; ++k_tile) {
        // кооперативная коалесцированная загрузка
        s_A[threadIdx.y][threadIdx.x] = A[row * N + (k_tile * TILE_DIM + threadIdx.x)];
        s_B[threadIdx.y][threadIdx.x] = B[(k_tile * TILE_DIM + threadIdx.y) * N + col];
        __syncthreads();                 // ждём загрузки тайла всеми
        #pragma unroll
        for (int k = 0; k < TILE_DIM; ++k)
            sum += s_A[threadIdx.y][k] * s_B[k][threadIdx.x];
        __syncthreads();                 // ждём вычислений перед перезаписью тайла
    }
    C[row * N + col] = sum;
}
```

**Разбор:**
- Поток `(ty, tx)` блока `(by, bx)` считает **один элемент** `C[row][col]`.
- Цикл по `k_tile` — проход **плиток вдоль общего измерения K**.
- Загрузка: поток грузит **по одному элементу** A и B → вместе блок загружает полные плитки.
  - `A[row*N + k_tile*T + tx]` — соседние `tx` = соседние адреса ✓ **коалесцировано**;
  - `B[(k_tile*T + ty)*N + col]` — соседние `tx` (через `col`) = соседние адреса ✓.
- **Два `__syncthreads()`:** 1-й — «плитка загружена» (чтение после записи), 2-й — «все закончили вычисления» (иначе быстрый поток перезапишет плитку на следующей итерации, пока медленные ещё читают — запись после чтения).
- Внутренний цикл читает Shared Memory: `s_A[ty][k]` — **все 32 потока варпа (одинаковый `ty`) читают один и тот же адрес → broadcast, конфликтов нет**; `s_B[k][tx]` — соседние потоки читают соседние слова → разные банки ✓.

> ⚠ **Ловушки кода:** (1) предполагается, что **N кратно TILE_DIM** (нет проверок границ → для общего случая нужны `if (row<N && …) ? … : 0`); (2) только **квадратные** матрицы (в формулировке GEMM M, N, K разные); (3) нет `α`, `β`; (4) `32×32 = 1024` потока — предельный размер блока, оставляет мало регистров на поток; (5) если бы `s_B` читался транспонированно (по столбцам с шагом 32) — были бы 32-way bank conflicts → лечение: `s[TILE][TILE+1]` (padding).
> ➕ **Ускорение по сравнению с наивным ядром** — обычно в 3–10 раз; до cuBLAS (≈ 10–20× выше наивного) ещё далеко.

## 6.4. Слайд 51 — Иерархический тайлинг: Shared → Registers

**Почему Shared Memory недостаточно для 100 % утилизации:**
- задержка Shared ≈ **20–30 тактов** (регистры — 0–1);
- ограничена пропускная способность портов Shared; риск bank conflicts;
- на каждый FMA нужно **2 чтения из Shared** (A и B) — отношение «чтение/вычисление» всё ещё велико.

**Решение — Thread Tiling (register blocking):**
- каждый поток считает **не 1 элемент, а микротайл** `C` (например 4×4 или 8×8), накапливая его **в регистрах**;
- **двухуровневое переиспользование:**
  1. Global → Shared: блок грузит плитки `BM × BK` и `BK × BN`;
  2. Shared → Registers: поток загружает вектор из `TM` элементов A и `TN` элементов B, и вычисляет **внешнее произведение** `TM × TN` (outer product, rank-1 update).

🧮 **Выигрыш:** для 4×4 за один шаг k: чтений из Shared **4 + 4 = 8**, FMA **16** → 2 FMA на одно чтение (было 0,5: 1 FMA на 2 чтения) → **в 4 раза** меньше нагрузка на Shared на FMA. Для 8×8: 16 чтений на 64 FMA = 4 FMA/чтение.

## 6.5. Слайд 52 — Код микротайлинга

```cuda
float reg_C[4][4] = {0.0f}, reg_A[4], reg_B[4];      // в регистрах (SROA)
for (int k_tile = 0; k_tile < N; k_tile += BK) {
    // 1. Загрузка тайла Global → Shared ...
    __syncthreads();
    // 2. По глубине BK
    for (int k = 0; k < BK; ++k) {
        #pragma unroll
        for (int m = 0; m < 4; ++m) reg_A[m] = s_A[k][thread_row_offset + m];
        #pragma unroll
        for (int n = 0; n < 4; ++n) reg_B[n] = s_B[k][thread_col_offset + n];
        // Rank-1 update целиком в РЕГИСТРАХ
        #pragma unroll
        for (int m = 0; m < 4; ++m)
            #pragma unroll
            for (int n = 0; n < 4; ++n)
                reg_C[m][n] += reg_A[m] * reg_B[n];     // 16 FMA без обращения к SMEM
    }
    __syncthreads();
}
```

**Что важно:**
- **SROA** (Scalar Replacement of Aggregates) — оптимизация компилятора: массивы `reg_C[4][4]`, `reg_A[4]`, `reg_B[4]` разбиваются на отдельные скаляры в регистрах — **только если все индексы известны на этапе компиляции** (циклы полностью развёрнуты `#pragma unroll`). Если индекс динамический — массив попадёт в **local memory** (медленно).
- `s_A[k][…]` — плитка A хранится **«транспонированной»** (индекс `k` первый), чтобы для фиксированного `k` 4 значения лежали подряд (можно читать одной векторной инструкцией `LDS.128`) и чтобы соседние потоки не конфликтовали.
- Регистров: 16 (аккумуляторы) + 8 (A, B) + индексы ≈ 30+; микротайл 8×8 → 64 аккумулятора + 16 — **давление на регистры** снижает occupancy; нужен баланс (типично 128×128 блок-тайл при 8×8 микротайле на 256 потоков).
- Реальные ядра (CUTLASS, cuBLAS) дополнительно используют **double buffering** (загрузка следующего тайла в Shared перекрывается с вычислением текущего; на Ampere — `cp.async`), векторные загрузки `float4`, swizzle раскладки Shared Memory.

## 6.6. Слайд 53 — Tensor Cores

- **Ограничение программного тайлинга:** обычные FPU/ALU выполняют **1 скалярный FMA** (`a·b + c`) за такт на нить.
- **Tensor Cores:**
  - аппаратный матричный конвейер внутри каждого SM;
  - работает на уровне **варпа (warp-level)**, а не отдельных нитей;
  - аппаратно умножает небольшие блоки: `D = A·B + C` (на слайде `A, B, C, D ∈ ℝ^{16×16}`).
- **Эволюция парадигмы:** скалярный код → векторизация → **матричные операции как примитив ISA**.

> ⚠ **Уточнения:** (1) На слайде «16×16» — это **WMMA-фрагмент**; нативная операция тензорного ядра меньше (на Volta — 4×4×4 на ядро; логический варп-блок 16×16×16 раскладывается на несколько инструкций). Фраза «за единый цикл инструкций» — упрощение. (2) Формы WMMA для `half`: **16×16×16, 32×8×16, 8×32×16**; TF32: 16×16×8; FP64 (A100): 8×8×4. (3) Типичная точность: входы **FP16/BF16/TF32/INT8/FP8** (в зависимости от архитектуры), **накопление в FP32** — смешанная точность. (4) Появились в **Volta (V100)**, развиты в Turing, Ampere (TF32, BF16, FP64), Hopper (FP8, `wgmma`, TMA).

## 6.7. Слайд 54 — WMMA API

```cuda
#include <mma.h>
using namespace nvcuda;
wmma::fragment<wmma::matrix_a, 16, 16, 16, half, wmma::row_major> a_frag;
wmma::fragment<wmma::matrix_b, 16, 16, 16, half, wmma::row_major> b_frag;
wmma::fragment<wmma::accumulator, 16, 16, 16, float> c_frag;
wmma::fill_fragment(c_frag, 0.0f);
for (int k = 0; k < K; k += 16) {
    wmma::load_matrix_sync(a_frag, &A[row * K + k], K);   // тайл A, шаг строки = K
    wmma::load_matrix_sync(b_frag, &B[k * N + col], N);   // тайл B, шаг строки = N
    wmma::mma_sync(c_frag, a_frag, b_frag, c_frag);       // матричное умножение на Tensor Cores
}
wmma::store_matrix_sync(&C[row * N + col], c_frag, N, wmma::mem_row_major);
```

**Разбор:**
- **`wmma::fragment<Use, M, N, K, Type, Layout>`** — «фрагмент» матрицы, **распределённый по регистрам потоков варпа** (структура содержимого скрыта).
- Роли фрагмента: `matrix_a`, `matrix_b`, `accumulator`.
- **`load_matrix_sync(frag, ptr, ldm)`** — загрузка тайла 16×16; `ldm` — **leading dimension** (шаг строки в элементах).
- **`mma_sync(D, A, B, C)`** — `D = A·B + C` на Tensor Cores.
- **`store_matrix_sync`** — запись аккумулятора обратно.
- Все функции **варп-коллективные**: **все 32 потока варпа обязаны** выполнить вызов одновременно (отсюда `_sync`).
- Входы `half`, аккумулятор `float` — **смешанная точность** (mixed precision).

> ⚠ **Ловушки/требования:** (1) переменные `row`, `col` в коде слайда не определены — это **координаты левого верхнего угла тайла 16×16 для данного варпа** (обычно вычисляются из `blockIdx`/`threadIdx` с делением на размер варпа); (2) `K` должно быть кратно 16; (3) `ldm` для `half` — кратно **8 элементам** (16 байт), указатели выровнены на **256 бит (32 байта)**; (4) требуется компиляция для **sm_70+** (`-arch=sm_70` и выше); (5) данные A и B должны быть в **half** (а не float) — нужна конвертация.
> ➕ **Простое ядро WMMA — не максимум:** для максимальной скорости используют **тайлинг в Shared + WMMA/mma.sync + double buffering** (CUTLASS/cuBLAS). Библиотеки сами выбирают Tensor Cores (`cublasGemmEx`, `cublasLt`, CUTLASS).

## 6.8. Слайд 55 — Сводка: иерархия оптимизаций GEMM

| Уровень | Где хранятся данные тайла | Основной лимитирующий фактор | Арифметическая интенсивность |
|---------|---------------------------|------------------------------|------------------------------|
| **Наивный GEMM** | Global Memory (DRAM) | Пропускная способность памяти (DRAM BW) | Минимальная (≈ 0,25 FLOP/B) |
| **Block Tiling** | Shared Memory (SRAM) | Задержки и конфликты банков SMEM | Средняя (≈ B/4 FLOP/B) |
| **Thread Tiling** | Регистровый файл нити | Число регистров на блок | Высокая (максимум для скалярных ALU) |
| **Tensor Cores (WMMA)** | Warp Registers / Matrix Units | Пропускная способность тензорных блоков | Пиковая (терафлопсы / петафлопсы) |

**Главный вывод:** **Tiling — универсальный принцип отображения N-мерных задач на иерархическую память GPU:**

```
DRAM  ⟹  Shared Memory  ⟹  Registers  ⟹  Tensor Cores
```

## 7.1. Все паттерны одной таблицей

| Паттерн | Идея | Work | Span | Узкое место | Главная оптимизация |
|---------|------|------|------|-------------|---------------------|
| **Map** | `y_i = f(x_i)` | O(N) | O(1) | память (DRAM BW) | коалесцирование, grid-stride, векторизация (`float4`), fusion |
| **Reduce** | свёртка в скаляр | O(N) | O(log N) | дивергенция, bank conflicts, межблочная агрегация | sequential addressing, **warp shuffle**, grid-stride накопление, 1 атомик/блок |
| **Scan** | префиксные суммы | O(N) (Blelloch/CUB), O(N log N) (Hillis–Steele) | O(log N) | межблочные зависимости | warp scan + decoupled look-back |
| **Stencil** | функция от соседей | O(N·|𝒩|) | O(1) на шаг | перекрытие обращений, halo | tiling + halo, cooperative load, L1/`__ldg`, текстуры |
| **Histogram/Scatter** | `H[f(x)]++` | O(N) | O(N) в худшем случае | contention атомиков | privatization, warp aggregation |
| **GEMM** | `C = A·B` | O(N³) | O(log N) | память → вычисления | block tiling → thread tiling → Tensor Cores |

## 7.2. Какая «память» в каждом паттерне играет главную роль

| Паттерн | Ключевой ресурс |
|---------|-----------------|
| Map | Global Memory, коалесцирование, векторизованные загрузки |
| Reduce | Shared Memory (банки), регистры (shuffle), L2 (атомики) |
| Scan | регистры (warp), Shared, глобальные дескрипторы с атомарной синхронизацией |
| Stencil | Shared (halo), L1/L2/Read-only cache, текстурный кэш |
| Histogram | L2 (атомики) → Shared (приватизация) → регистры (aggregation) |
| GEMM | Shared → регистры → Tensor Cores |

## 7.3. Частые «подводные камни» общего характера

- **`__syncthreads()` в условном коде:** все потоки блока должны достичь барьера → нельзя ставить внутри `if (tid < s)` (в слайдах он стоит **вне** `if` — правильно).
- **Неинициализированная Shared Memory:** её содержимое — мусор; перед использованием обнуляйте (гистограмма) и/или заполняйте нейтральным элементом (редукция неполного блока).
- **Нейтральный элемент для неполных блоков:** 0 для суммы; `-INFINITY` для max; `INFINITY` для min.
- **Гонки при «in-place»:** scan Хиллса–Стила, stencil → двойной буфер.
- **Volta+ и независимое планирование потоков:** не рассчитывайте на неявную синхронность внутри варпа; `__shfl_*_sync`, `__syncwarp()`, явные маски.
- **Целочисленное переполнение `int`** в индексах при больших N → `size_t`.
- **Детерминизм float:** атомики и разный порядок суммирования → разные результаты.
- **Профилирование:** сначала **nsys** (где время), потом **ncu** (почему ядро медленное: memory vs compute bound, bank conflicts, divergence, achieved occupancy).

# ЧАСТЬ 9. Вопросы для самопроверки (с ответами)

## Map
1. **Что такое Map и почему он «embarrassingly parallel»?** — Независимое применение чистой функции к каждому элементу; нет зависимостей, синхронизаций и атомиков.
2. **Почему Map почти всегда memory-bound?** — Очень мало FLOP на байт (напр., 1 FLOP на 8 байт); скорость определяется пропускной способностью DRAM.
3. **Что такое Grid-Stride Loop и чему равен `stride`?** — Каждая нить обрабатывает элементы `tid, tid+stride, …`; `stride = blockDim.x × gridDim.x`.
4. **Сохраняется ли коалесцирование в grid-stride?** — Да: на каждой итерации соседние нити обращаются к соседним адресам.
5. **Как подобрать размер сетки в grid-stride?** — `num_SMs × блоков на SM` (по occupancy).
6. **Зачем запуск `<<<1,1>>>` при отладке?** — Один поток последовательно обходит массив → эталонный результат для сверки.
7. **Что такое векторизация доступа и какие типы?** — Чтение/запись `float4/int4` (128 бит) вместо `float`; меньше инструкций, ближе к пику DRAM.
8. **Какое требование к адресу для `float4`?** — Кратность 16 байтам; `cudaMalloc` даёт ≥ 256.
9. **Что делать с хвостом при `N % 4 ≠ 0`?** — Обработать оставшиеся элементы скалярным циклом.
10. **Что такое register spilling?** — Нехватка регистров → переменные уходят в local memory (медленно).
11. **Зачем `__restrict__`?** — Обещание отсутствия алиасинга → больше оптимизаций, использование read-only кэша.

## Reduce
12. **Какие свойства оператора нужны для параллельной редукции?** — Ассоциативность (обязательна), коммутативность (даёт свободу порядка).
13. **Work и span редукции?** — W = O(N), S = O(log N).
14. **Почему сумма `float` на GPU может отличаться от CPU?** — Сложение float не ассоциативно; порядок суммирования разный.
15. **В чём дефект V1?** — Warp divergence из-за `tid % (2*s) == 0` (при `s=1` 50 % простоя, `s=2` — 75 %, … до ~97 %), плюс дорогой `%`.
16. **Как V2 устраняет дивергенцию и что получает взамен?** — Индекс `2*s*tid` группирует активных потоков в начале; появляются bank conflicts (2-way, 4-way, … растущие).
17. **Почему V3 идеальна по Shared Memory?** — `tid < s`, `sdata[tid + s]` — линейный доступ → нет дивергенции (целые варпы) и нет конфликтов банков.
18. **Что остаётся неэффективным в V3?** — Половина потоков простаивает уже на первом шаге (лечится «first add during load»).
19. **Что делает `__shfl_down_sync(mask, val, offset)`?** — Берёт `val` у потока `lane+offset` внутри варпа через регистры.
20. **Сколько шагов у warp-редукции и результат где?** — 5 шагов (offset 16,8,4,2,1); сумма в lane 0.
21. **Что такое mask в `_sync`-функциях?** — Набор потоков, обязанных участвовать; все они должны выполнить вызов.
22. **Почему `__shfl_down` без `_sync` нельзя с Volta?** — Independent Thread Scheduling: lock-step в варпе не гарантирован; нужна явная маска.
23. **Почему `warp_sums[32]`?** — Максимум 1024 потока = 32 варпа → 32 частичные суммы, их хватает одному варпу для финальной редукции.
24. **Чем атомики хуже/лучше two-pass для межблочной редукции?** — Атомик: один запуск, но сериализация и недетерминизм; two-pass: детерминизм и масштаб, но второй запуск и доп. буфер.
25. **Как обеспечить детерминизм float-редукции?** — Фиксированное дерево (two-pass или last-block), не использовать `atomicAdd` для float.
26. **Как редуцировать за один проход без атомиков суммы?** — `__threadfence()` + счётчик «последнего блока» (threadFenceReduction).
27. **Почему grid-stride полезен в редукции?** — Поток накапливает много элементов в регистре перед деревом → меньше блоков и меньше глобальных операций.

## Scan
28. **Inclusive vs exclusive scan?** — Inclusive включает текущий элемент; exclusive — только предшествующие, `y₀ = I`.
29. **Пример scan для `[3,1,7,0,4]`?** — Inclusive `[3,4,11,11,15]`; exclusive `[0,3,4,11,11]`.
30. **Как из inclusive получить exclusive?** — Сдвинуть вправо на 1 с подстановкой нейтрального элемента.
31. **Зачем scan нужен?** — Compaction, radix sort, смещения для динамической записи, CSR `row_ptr`, BVH.
32. **Work и span Хиллса–Стила?** — W = O(N log N), S = O(log N); не work-efficient.
33. **Work и span Блеллока?** — W = O(N), S = O(log N) (≈ 2 log N).
34. **Из каких фаз состоит Блеллок?** — Up-sweep, обнуление корня, down-sweep.
35. **Какую форму scan строит Блеллок?** — Exclusive.
36. **Какой алгоритм использовать на уровне варпа и почему?** — Hillis–Steele через `__shfl_up_sync`: 5 шагов, регистры, без барьеров; лишняя работа не важна при N = 32.
37. **Что делает `__shfl_up_sync`?** — Поток `lane` получает значение от `lane − delta`.
38. **Три прохода Block-Scan-Add?** — Локальный scan тайлов + суммы блоков; scan сумм; прибавление префикса к тайлам.
39. **Недостаток Block-Scan-Add?** — ~3× трафик памяти и 3 запуска ядра.
40. **Идея decoupled look-back?** — Single-pass; блоки берут тайлы по атомарному счётчику, публикуют статусы (A/P; X — не готов), оглядываются назад до первого P.
41. **Зачем атомарный счётчик для тайлов?** — Гарантирует, что предшественники уже запущены → нет deadlock.
42. **Как делается Stream Compaction?** — Предикат → exclusive scan → scatter; размер = `idx[N−1] + b[N−1]`.
43. **Почему не `atomicAdd`-счётчик для compaction?** — Не сохраняет порядок и сериализует; scan даёт упорядоченную плотную упаковку.

## Stencil
44. **Что такое stencil?** — Новое значение элемента — функция его и фиксированных соседей предыдущего шага.
45. **Что такое halo/ghost cells?** — Кайма шириной R вокруг тайла, нужная для расчёта краёв; только читается.
46. **Размер Shared Memory для тайла?** — `(Tx+2R)(Ty+2R)·sizeof(Element)`; для 16×16 и R=1 — 18×18.
47. **Типы краевых условий?** — Дирихле (константа), Неймана (clamp/нулевой градиент), периодические (mod W).
48. **Почему наивная догрузка halo плоха?** — Divergence в краевых варпах и некоалесцированные вертикальные границы.
49. **Что такое кооперативная загрузка?** — Тайл как 1D-массив; потоки по циклу `i = tid; i < N_shm; i += N_threads` грузят его без ветвлений.
50. **Чем плох «раздутый блок потоков»?** — Halo-потоки простаивают при вычислении; возможен выход за 1024 потока.
51. **Что делает `__ldg()`/`const __restrict__`?** — Загрузка через read-only кэш, no aliasing.
52. **Плюсы и минусы текстур для stencil?** — Плюс: 2D-кэш, аппаратные границы (clamp/wrap); минус: сложный API, только чтение, ограничения типов.
53. **Что такое Z-порядок?** — Индекс Мортона — чередование бит x и y; даёт 2D-локальность.
54. **`morton(5,3)`?** — 27 (x=101₂ → 17, y=011₂ → 10).
55. **Когда Wrap/Mirror в текстурах работают?** — Только с нормализованными координатами.
56. **Зачем нужен ping-pong буфер?** — Чтобы не читать уже обновлённые соседние значения (гонка).

## Scatter/Gather, Histogram
57. **Gather vs scatter?** — Gather — нерегулярное чтение, нет конфликтов записи; scatter — нерегулярная запись, возможны гонки.
58. **Почему гистограмма — scatter?** — Потоки инкрементируют корзины по вычисляемому индексу; разные потоки могут попасть в одну ячейку.
59. **Почему наивная гистограмма медленная?** — Атомики к одной ячейке сериализуются в L2; худший случай O(N).
60. **Что такое приватизация?** — Локальные копии (подгистограммы в Shared Memory) + финальное слияние в Global.
61. **Во сколько раз приватизация уменьшает число глобальных атомиков?** — С M элементов до B корзин на блок.
62. **Ограничения приватизации?** — Размер Shared Memory (B·4 байт), bank conflicts, внутриблочная конкуренция при дисбалансе.
63. **Что такое warp aggregation?** — Лидер варпа делает один атомик с весом = числу потоков с таким же bin.
64. **Роль `__match_any_sync`, `__popc`, `__ffs`?** — Маска совпавших потоков; число совпадений; номер лидера.
65. **С какой архитектуры `__match_any_sync`?** — Volta (CC 7.0).
66. **Что выбрать при огромном числе корзин?** — Direct warp aggregation в Global либо sort + reduce_by_key.
67. **Какая стратегия при малом B и сильных выбросах?** — Warp Aggregated Privatization.

## GEMM
68. **Сколько FLOP в GEMM N×N×N?** — 2N³.
69. **Арифметическая интенсивность наивного GEMM?** — 0,25 FLOP/байт (memory-bound).
70. **Как тайлинг B×B меняет интенсивность?** — До B/4 FLOP/B; при B=32 → 8 FLOP/B (в 32 раза).
71. **Зачем два `__syncthreads()` в тайловом цикле?** — Первый: данные загружены; второй: все закончили вычисления до перезаписи тайла.
72. **Почему `s_A[ty][k]` не вызывает bank conflict?** — Все потоки варпа читают один адрес → broadcast.
73. **Что такое thread tiling?** — Поток считает микротайл C (напр. 4×4) в регистрах через внешнее произведение.
74. **Сколько FMA на чтение из Shared при 4×4?** — 16 FMA на 8 чтений = 2.
75. **Что такое SROA и почему важен `#pragma unroll`?** — Замена массива на регистры; работает при константных индексах.
76. **Что такое Tensor Core?** — Аппаратный матричный блок SM, работающий на уровне варпа.
77. **Что делают `load_matrix_sync`, `mma_sync`, `store_matrix_sync`?** — Загрузка тайла в фрагмент, умножение-накопление на Tensor Cores, сохранение результата; все варп-коллективные.
78. **Типы данных в примере WMMA?** — Входы `half`, аккумулятор `float`.
79. **Главный вывод по GEMM?** — Tiling: DRAM → Shared → Registers → Tensor Cores.

## Общие
80. **Что такое work-efficient?** — W параллельного алгоритма того же порядка, что у лучшего последовательного.
81. **Какие паттерны здесь memory-bound по умолчанию?** — Map, Stencil, наивный GEMM, наивная гистограмма (из-за contention).
82. **Что общего у тайлинга в stencil и GEMM?** — Загрузка блока данных в Shared Memory для многократного переиспользования потоками блока.
83. **Какие барьеры синхронизации используются и где?** — `__syncthreads()` (блок), `_sync`-примитивы/`__syncwarp()` (варп), конец ядра (глобально).
84. **Как профилировать узкие места этих паттернов?** — nsys → где время; ncu → memory vs compute bound, bank conflicts, divergence, occupancy, атомики.

# ЧАСТЬ 10. Шпаргалка для повторения в последний момент

- **Map:** `y_i = f(x_i)`; embarrassingly parallel; memory-bound; **grid-stride** (`stride = blockDim.x·gridDim.x`), **`float4`** (выравнивание 16 Б, хвост!), `__restrict__`, `grid = SMs × blocks/SM`.
- **Reduce:** ассоциативность+коммутативность; W = O(N), S = O(log N). **V1** `tid % 2s` → divergence; **V2** `index = 2·s·tid` → bank conflicts; **V3** `tid < s` (sequential) ✓; **warp shuffle** `__shfl_down_sync` (offset 16→1, результат в lane 0); межблочно: `atomicAdd` (быстро, недетерминированно) vs two-pass (детерминированно). Volta+: только `_sync`.
- **Scan:** inclusive `[3,4,11,11,15]`, exclusive `[0,3,4,11,11]` для `[3,1,7,0,4]`. **Hillis–Steele:** O(N log N), warp-уровень, `__shfl_up_sync`, 5 шагов. **Blelloch:** O(N), up-sweep → обнуление → down-sweep, exclusive. **Block-Scan-Add:** 3 прохода. **Decoupled look-back:** single-pass, A/P (+X), атомарный счётчик тайлов (CUB). **Compaction:** predicate → exclusive scan → scatter.
- **Stencil:** `u^{t+1} = c₀u + Σ c·соседи`; тайл `(Tx+2R)(Ty+2R)`; halo; границы: Дирихле / Нейман (clamp) / периодика; кооперативная загрузка (цикл по плоскому индексу); альтернативы: L1+`__ldg`, текстуры (clamp/wrap, Z-order); ping-pong буферы.
- **Histogram:** gather (чтение, без гонок) / scatter (запись, гонки). Naive `atomicAdd` в Global → сериализация O(N). **Privatization** (Shared, B·4 байт) → **Warp aggregation** (`__match_any_sync`, `__popc`, `__ffs`, лидер) → direct warp aggregation / sort+reduce_by_key для огромных B.
- **GEMM:** 2N³ FLOP; naive I = 0,25 FLOP/B; block tiling I = B/4 (B=32 → 8); thread tiling (outer product в регистрах, 4×4 → 2 FMA/чтение); Tensor Cores (WMMA: fragment, load/mma/store_matrix_sync; half → float).
- **Главное:** «**Tiling**: DRAM ⟹ Shared Memory ⟹ Registers ⟹ Tensor Cores».
