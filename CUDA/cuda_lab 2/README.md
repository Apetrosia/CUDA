# CUDA lab: scalar products of corresponding rows

Здесь приведены два варианта решения:

- `dot_rows_slow.cu` — один поток считает одно скалярное произведение строки;
- `dot_rows_shared.cu` — один warp считает одну строку, чтения из глобальной памяти коалесцированы, а частичные суммы складываются через shared memory.

Обе программы:

- генерируют случайные входные данные на CPU (`std::mt19937`, seed задается параметром);
- автоматически строят CPU reference;
- измеряют среднее время kernel через CUDA Events;
- проверяют результат с допуском;
- печатают конфигурацию launch и расчетные GFLOP/s и GB/s.

## Сборка

```bash
"C:\Program Files (x86)\Microsoft Visual Studio\18\BuildTools\VC\Auxiliary\Build\vcvarsall.bat" x64
nvcc -O2 -lineinfo dot_rows_slow.cu   -o dot_rows_slow
nvcc -O2 -lineinfo dot_rows_shared.cu -o dot_rows_shared
```

## Запуск

```bash
./dot_rows_slow 4096 4096 100 12345
./dot_rows_shared 4096 4096 100 12345
```

Аргументы: `rows cols iters seed`.

Для стабильной профилировки используйте одинаковые `rows`, `cols` и `seed` у обоих вариантов. Значение `iters=100` удобно для тайминга, а при Nsight Compute можно дополнительно запустить один и тот же бинарник с теми же размерами.

## Nsight Compute

В GUI укажите соответствующий executable. Для CLI-проверки перед отчетом полезно получить базовые метрики, например:

```bash
ncu --set full -o slow_ncu ./dot_rows_slow 4096 4096 100 12345
ncu --set full -o shared_ncu ./dot_rows_shared 4096 4096 100 12345
```

Точные имена отдельных метрик зависят от версии Nsight Compute и архитектуры GPU, поэтому окончательные числа в отчете нужно брать из интерфейса вашей лабораторной машины.

## Roofline

Для одной строки из `K` элементов выполняется примерно `2K` FLOP (умножение + сложение на элемент) и читаются `2K` чисел `float`, плюс запись одного результата. Поэтому алгоритмическая интенсивность:

`I(K) = 2K / (8K + 4) FLOP/byte`,

то есть при больших `K` она стремится к `0.25 FLOP/byte`.

Положение Roofline определяется как

`P <= min(P_peak_compute, I * BW_memory)`.

Низкая измеренная производительность простого ядра обычно объясняется не самой формулой Roofline, а тем, что оно не приближается к пиковой пропускной способности памяти: соседние потоки warp обращаются к элементам разных строк, поэтому глобальные загрузки плохо коалесцируются. Быстрый вариант меняет соответствие "поток -> данные": 32 соседних потока одного warp читают соседние элементы одной строки.

Важно: shared memory здесь не дает значительного повторного использования данных между строками. Ее основная роль — организовать редукцию частичных сумм внутри блока; главное ускорение ожидается от коалесцированных глобальных загрузок.
